# 亿级规模审计

> 审计对象：`distledger` 的全部热路径，在**亿级**数据量下的行为。
> 审计日期：2026-09-14 ｜ 对应版本：v0.3 + 存储模块化地基
>
> 这份文档回答一个问题：**这套设计在 10 亿行规模上还成立吗？**
> 结论分三类：**已修复**、**已定方案未实现**、**可接受并说明理由**。

---

## 0. 规模假设

| 维度 | 取值 |
|---|---|
| 佣金记录 | 10 亿行 |
| 资金流水 | 10 亿行 |
| 账户 | 5000 万行 |
| 租户 | 5000 |
| 订单峰值 | 5000 TPS |
| 硬件 | NVMe，随机 5 万 IOPS，索引顺序扫描 ~1 GB/s |
| 页面 | 16 KB，B+ 树 10 亿行约 4 层 |

索引条目按 30 字节估算：10 亿行的 `(state, available_at, tenant_id)` 覆盖索引约 **30 GB**。

---

## 1. 结论摘要

| # | 热路径 | 原设计在亿级 | 状态 |
|---|---|---|---|
| A | 单笔分佣 `OnOrderPaid` | O(log n)，可接受 | ✅ **可接受**，但索引数量是写放大乘数 |
| B | 心跳 `Maintain` | **O(租户数) 次事务/ tick**，5000 租户 ≈ 5–15 秒纯开销 | ✅ **已修复**（ADR-035） |
| C | 到期查询 | 修前依赖租户索引，跨租户扫描退化为 O(积压) | ✅ **已修复**（换索引列序） |
| D | 自检 `SelfCheck` | **客户端逐行流式**，10 亿流水 ≈ 数小时 | ⏳ **已定方案未实现** |
| E | 账户行热点 | 高单量下同一账户行乐观锁冲突 → 事件级重试 | ✅ **已修复**（端口新增原子增量） |
| F | 索引预算 | 5 棵 B+ 树/ INSERT，写放大 | 📄 **说明 + 裁剪建议** |
| G | 归档与分区 | 未考虑 | 📄 **给出建议** |

**一句话**：心跳与账户热点已修；自检的聚合下推是唯一**已识别但尚未实现**的债务，方案写在下面；其余在给定假设下可接受。

## 2. 已修复：心跳（B、C）

### 2.1 问题

原 `Maintain`：

```go
tenants := r.Tenants(ctx)            // 列出全部租户
for _, t := range tenants {
    l.maintainTenant(ctx, t, now)    // ← 每个租户开一次事务，无论有没有活
}
```

5000 租户 → 每分钟 5000 次 `BeginTx`/`Commit`，即使**全库没有任何到期佣金**。
按每次 1–3 ms 估算，纯开销 **5–15 秒/分钟**，而且这 5000 次事务在数据库侧产生 5000 个事务 ID 与相应的 undo/redo。

更糟的是它随租户数线性增长：**1 万租户翻倍，10 万租户直接不可用**。

根因不是「取租户列表慢」——我上一版修的是这个，那只把每次事务前的扫描换成了索引查找，**成本结构没变**。
真正的问题是**端口问错了问题**：

> 它问「有哪些租户」，而引擎需要的是「有哪些活」。

### 2.2 修法

端口方法换成：

```go
TenantsWithDueWork(ctx context.Context, dueAt time.Time, limit int) ([]int64, error)
```

引擎的 tick 变成：

```
重复直到无进展或达到工作预算：
    取「有到期佣金的租户」（一次索引范围扫描，上限 500）
    对每个这样的租户：结算，失败按租户隔离
```

**无到期项时：1 次索引查找，0 次事务。** 有 N 个租户有活时：O(N)。

### 2.3 索引列序是承重的

到期索引的列序从 `(tenant_id, state, available_at, id)` 改为 **`(state, available_at, tenant_id)`**。

这不是风格问题：跨租户查询若以 `tenant_id` 打头，会退化为**扫描排在最前面的那个租户的全部积压**——
一个租户的积压会拖慢所有其它租户的心跳（噪声邻居）。列序换过来之后，两个查询都是索引范围扫描。

`schema_test.go` 里有一条测试**直接断言这个列序**，因为改列序在功能上不会报错，只会在压力下变慢。

### 2.4 用测试固定成本，而不是固定结果

结算结果在「按租户循环」和「按工作循环」两种实现下**完全一样**，所以任何断言结果的测试都看不出区别。
差别只在规模上暴露——那是最不该发现它的地方。

因此新增的测试**数操作次数**：

| 场景 | 断言 |
|---|---|
| 1 / 50 / 500 个空闲租户，无到期项 | **恰好 1 次读，0 次事务** |
| 200 个租户中仅 3 个有活 | 事务数与读数都是个位数 |

这条测试的价值在于：**成本性质一旦退化，它会立刻失败**，而不是等到生产环境出现 5000 个租户。

### 2.5 工作预算：一个共享的额度，不是一个「每层循环的上限」

单次 `Maintain` 有显式上界：

| 常量 | 值 | 含义 |
|---|---|---|
| `maintainBatch` | 200 | 单个事务处理的佣金数 |
| `maintainWorkBatch` | 2000 | 一次发现读返回的到期佣金数 |
| `maxMaintainRounds` | 100 | 单次调用的轮数上限 |
| `maxSettlePerMaintain` | 20000 | **单次调用的结算笔数预算** |

积压通过多次 tick 消化，而不是把一次定时任务拖到超时。

**但「有上界」这句话曾经是错的。** 原来的实现只在**外层轮次的开头**检查预算：

```
for round := 0; round < maxMaintainRounds; round++ {
    if total.SettledCount >= maxSettlePerMaintain { break }   // ← 只在这里
    ...
    for _, group := range groupByTenant(batch) {
        part := l.maintainTenant(...)   // 每个租户内部还能再结算 100 × 200
    }
}
```

内层每个租户最多结算 `maxMaintainRounds × maintainBatch = 20000` 笔，而外层对这一批里的**每个租户**都调用一次。
也就是说：**真正的上限是「租户数 × 20000」，而不是 20000。** 40 个租户的批就是 80 万笔。

这不是理论推导，`scale_test.go` 里用 30 个租户 × 900 笔（共 27000 笔到期）实测到：

```
one Maintain call settled 27000 commissions; the budget is 20000
```

**修法**：预算变成一个 `workBudget` 对象，被两层循环共享，谁花的谁记账：

- 只有**事务提交之后**才记账（`budget.spend`）。store 可能重跑整个闭包来回滚重试，在闭包里扣账会把回滚掉的工作也算进去。
- 读取也受预算约束（`budget.permits`），而不是只约束写入——否则预算只剩 3 笔时仍会去读满一批 200 笔。
- 外层在**每个租户之前**检查额度，而不是在一轮之后。少一次检查，就多一整轮乘以租户数的超支。

这条测试断言的是**预算被用满**（`== 20000`），而不只是「没超过」：否则一个被别的 bug 悄悄压成 0 的预算也能通过。

### 2.6 配额与工作发现的实测数据

`integration/explain_test.go` 的探针现在铺 80000 笔到期佣金（40 租户），`available_at` **按分钟铺开**，
因为所有行共用一个时间戳会让 InnoDB 报告该列 cardinality = 1，优化器随即失去选择有序索引的理由——
那时量到的是造的数据，不是查询。铺开之后（MySQL 8.4）：

| 场景 | 计划 | 行数 | 耗时 |
|---|---|---|---|
| **无到期（常态 tick）** | `idx_4` 覆盖索引范围扫描，**无排序** | **0** | **298 µs** |
| 一小时到期 | `idx_4` 覆盖索引范围扫描，无排序 | 61 | 275 µs |
| 一天到期（满一批） | `idx_4` 覆盖索引范围扫描，无排序 | 1441 | 505 µs |
| 全表到期（积压） | `idx_3` 覆盖索引跳跃扫描 + **排序 80000 行** | 2000 | 9.8 ms |
| 旧写法（租户发现） | `idx_3` 查找 + Group | 40 | 6.3 ms |

**常态成本是 O(limit)，不是 O(表)**：没有到期项时是一次「空的范围查找」，298 µs，与表里有多少行无关。
这正是每分钟跑一次所需要的性质。

积压场景是唯一的退化点：MySQL 估计 `rows=11872`（实际 80000），于是放弃有序索引去扫全表再排序。
用 `FORCE INDEX (dist_commission_idx_4)` 强制之后变成读 2000 个索引条目、**0.33 ms，快 30 倍且不再排序**。

**刻意没有加索引提示**：常态路径本来就已经是最优计划，积压是暂态；而 MySQL 的 `FORCE INDEX` / SQLite 的
`INDEXED BY` 各写一套只为讨好一个后端的优化器，不划算。这里记录的是「退化时知道往哪看」。

### 2.7 索引名不再由位置决定

上面那个 `idx_4` 曾经是**按位置**命名的（`table_kind_序号`）。这是潜伏的坑：

索引名一旦编码「它在列表里排第几」，列表一变它就换了含义。老版本迁移出来的库里
`dist_commission_idx_3` 是旧的列组合，而按新列表新建的库里同名索引是**另一组列**。
同一版本、两个部署、一个标识符指向两种东西——而索引名正是唯一声称能标识它的东西。

现在索引名由**列**推导（`table_idx_state_available_at_id`）：名字是定义的函数，不会漂移，
而且 EXPLAIN 输出里能自解释。`schema_test.go` 断言两条性质：名字等于列推导结果，且**重排列顺序不会改名**。

## 3. 已识别但未实现：`SelfCheck`（D）

### 3.1 问题

`SelfCheck` 目前在**客户端**逐行对账：

```
分页遍历账户
  对每个账户：分页遍历它的全部流水，累加四个桶
  与账户当前值比对
```

工作量 O(账户数 + 流水数)，但更致命的是**往返次数**：10 亿行流水，即使批量 1000，也需要 **100 万次**数据库往返。
按每次 0.5 ms 计约 **8 分钟**（理想情况），实际含扫描与排序更可能是**数小时**。
而且整个过程持有读事务/连接。

**在当前形态下，10 亿行规模的自检不可用。**

### 3.2 方案

把对账**下推到数据库**，只把不一致的行传回客户端：

```sql
SELECT a.tenant_id, a.user_id, a.frozen, a.available, ..., 
       COALESCE(l.sf, 0), COALESCE(l.sa, 0), ...
FROM dist_account a
LEFT JOIN (
    SELECT user_id,
           SUM(delta_frozen)    AS sf,
           SUM(delta_available) AS sa,
           ...
    FROM dist_ledger
    WHERE tenant_id = ?
    GROUP BY user_id
) l ON l.user_id = a.user_id
WHERE a.tenant_id = ?
  AND (a.frozen <> COALESCE(l.sf, 0) OR a.available <> COALESCE(l.sa, 0) OR ...)
LIMIT ?
```

`(tenant_id, user_id, id)` 索引是覆盖索引，数据库做一次索引全扫 + 哈希聚合。
**10 亿行在数据库内聚合是它的强项**（分钟级），而客户端只收到**不一致的行**——正常情况是零行。

端口侧的形状：

```go
// Reconciler 是可选接口：存储层用它自己的聚合能力完成账户与流水的对账，
// 而不是把每一行都流经客户端。
type Reconciler interface {
    ReconcileAccounts(ctx context.Context, tenantID int64, fn func(AccountMismatch) error) error
}
```

与 `SchemaChecker` / `ReportedStore` 同一模式：**实现了就参与，没实现就退回逐行路径**。
内存实现不实现它（内存里逐行就是最优），SQL 实现必须实现。

> **为什么不现在实现**：`Reconciler` 需要 SQL store 主体（尚未编写）。
> 定义一个没有实现者的接口就是空壳——正是本项目一直在清理的东西。
> 因此它与 v0.4 的 store 主体一起落地。

## 4. 已修复：账户行热点（E）

### 4.1 问题

`creditAccrual` 与 `settleOne` 原本做**读-改-写**：

```
读 Account → 改两个桶 → PutAccount（带 version CAS）
```

高单量下大量订单归属于同一个热门分销员（头部 KOL、大团长），同一账户行被并发更新：
版本不匹配 → `ErrConflict` → 整个 `OnOrderPaid` 事件重试。幂等保证了不会算错钱，
但吞吐随热点集中度下降，而**热点集中正是分销业务的常态**。

### 4.2 修法

端口新增原子增量：

```go
type AccountDelta struct {
    Key UserKey
    Frozen, Available, Withdrawing, Withdrawn Money
    TotalEarned, TotalReversed Money
    At time.Time
    // 会令任何桶变成负数时，整笔拒绝并返回 ErrInsufficientBalance
    RequireNonNegative bool
}

IncrementAccount(ctx context.Context, delta AccountDelta) (Account, error)
```

引擎的三处资金变动全部改用增量：分佣入账、结算、冲正扣款。

`PutAccount` 保留但语义收窄为**管理性调整**——运维把余额设成某个确定值。
它正是自检要抓的那个形态（有人改了余额却忘了写流水），因此自检测试用它注入损坏数据。

### 4.3 两个关键设计点

**守卫必须在同一条语句内。** `RequireNonNegative` 不是先读出来比较再写，
而是作为 `UPDATE ... WHERE frozen + ? >= 0 AND ...` 的谓词。先检查再写入是两个语句，
中间可以插入别的写者——这个窗口在结算与冲正上就是丢钱。

**为什么用增量而不是「重试 CAS」。** 重试让每个写者都要处理失败，
而增量让数据库用自己的行锁串行化它们：没有版本冲突、没有重试、也不可能静默覆盖。
在热门账户上这不是微优化，是量级差别。

### 4.4 验证

`TestEngineConcurrentOrdersToOneAgent`：12 个订单**全部归属同一个分销员**，并发提交。

断言不只是「没有错误」，而是「算术精确」：

- 失败的订单数必须为 **0**（旧的读-改-写在此处会产生冲突）
- 最终余额必须**恰好**等于各笔之和

加上「算术精确」这一条，是因为丢失更新表现为**少钱**而不是报错——
只断言无错误的测试会放过它。

四个后端全部通过。

## 5. 索引预算与写放大（F）

`dist_commission` 每插入一行要更新 **5 棵 B+ 树**（1 主键 + 4 二级）。10 亿行时每棵约 20–30 GB。

| 索引 | 服务谁 | 可否裁剪 |
|---|---|---|
| `PRIMARY KEY (id)` | 主键、生成 ID | ❌ 必需 |
| `UNIQUE (tenant_id, idem_key)` | **幂等性** | ❌ 必需，是 `ErrDuplicate` 的唯一依据 |
| `(tenant_id, order_id)` | 分佣、收货、退款都要查整单 | ❌ 热路径，必需 |
| `(state, available_at, tenant_id)` | 心跳 | ❌ 必需 |
| `(tenant_id, id)` | `CommissionsByTenant`，仅自检与对账用 | ⚠️ 可裁，代价是自检退化为扫描 |
| `(tenant_id, agent_user_id, id)` | 分销员佣金列表（用户可见页面） | ⚠️ 可裁，代价是列表页变慢 |

**建议**：把最后两项在部署文档里标为「按需保留」。
如果自检已改用 §3 的聚合方案，`(tenant_id, id)` 的必要性下降；
如果佣金列表页可以接受分页更慢，`(tenant_id, agent_user_id, id)` 也可以去掉。

**每减一个索引，插入路径少一棵 B+ 树维护。** 在 10 亿行规模上这是实打实的收益。

### 一条反直觉但重要的结论

**为了读优化而加的索引，成本落在写上，而写是这个系统的主要负载。**
分佣是持续写入的路径，自检是每天一次的离线任务。
**不要为了每天一次的任务给每秒数千次的写入加索引。**

## 6. 归档与分区（G）

| 数据 | 建议 |
|---|---|
| `dist_commission`（已结算/已冲正且过售后期） | 可按 `accrued_at` 范围分区，冷分区可迁至低成本存储 |
| `dist_ledger` | **不可删除**——复式记账的完整性依赖它。按 `created_at` 或 `tenant_id` 分区 |
| `dist_account` | 行数等于有收益的分销员数，通常远小于流水，不需要分区 |
| `dist_refund` | 行数远小于佣金，不需要分区 |

分区的主要收益不是省空间，而是**把索引高度压下来**：每个分区有独立的 B+ 树，
4 层变 3 层意味着每次查找少一次页访问——在 5000 TPS 上这很可观。

**注意**：分区键一旦选定，`UNIQUE (tenant_id, idem_key)` 这类约束在 MySQL 下**必须包含分区键**。
按 `accrued_at` 分区会与幂等唯一约束冲突。因此：
- 若按 `tenant_id` 哈希分区 → 幂等唯一约束保持有效 ✅
- 若按时间范围分区 → 幂等唯一约束无法跨分区，**不可行** ❌

**结论：`dist_commission` 应按 `tenant_id` 哈希分区，而不是按时间。**

## 7. 其它路径

| 操作 | 复杂度 | 亿级评估 |
|---|---|---|
| `OnOrderPaid` | O(级数 × log n) 次索引查找 | ✅ 级数 ≤ 3，可接受 |
| `OnOrderReceived` | 1 次订单查询 + 每笔佣金 1 次 UPDATE | ✅ |
| `OnOrderRefunded` | 1 次订单查询 + 1 次退款查询 + 每笔佣金 2 次写 | ✅ |
| `CommissionsByOrder` | `(tenant_id, order_id)` 索引，O(结果) | ✅ |
| `CommissionsByAgent` | 键集分页，O(limit) | ✅ |
| `LedgerEntries` | 键集分页，O(limit) | ✅ |
| `CountCommissionsByState` | `(state, ...)` 聚合，O(该租户佣金数) | ⚠️ 1 亿行租户约 1 秒；属离线路径，可接受 |
| `Balance` | 主键查找 | ✅ |

**键集分页不是风格选择而是正确性要求**（ADR-021）：`OFFSET` 分页在翻页途中有写入时会漏读，
而对账漏读等于「账是平的」这个结论不成立。

## 8. 尚未验证的部分（诚实声明）

这份审计是**基于复杂度与索引结构的推算**，不是实测。以下都必须用真实数据库验证：

1. §2 的心跳成本 —— 测试固定了**操作次数**，真实数据库上的每次操作耗时未测
2. §3 的聚合对账 SQL —— 尚未编写，10 亿行上的实际耗时未知
3. §5 的索引裁剪效果 —— 未在真实数据量上测量写吞吐差异
4. §6 的分区方案与幂等唯一约束的交互 —— 需要按目标数据库实测

**任何一条在验证后与本文档不符，都应当回来修订本文档，而不是悄悄按旧结论继续。**
