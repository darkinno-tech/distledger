# 不变量

这份文档是**照着代码写的**，不是照着希望写的。每一条都给出：它保证什么、为什么必须成立、
由什么强制、以及**它不覆盖什么**。

最后一项最重要。一个不变量文档最容易造成的伤害，是让人以为「自检通过」等于「账目正确」。
实际上每条不变量都有明确的盲区，把它们写清楚比把保证写漂亮更有用。

读取方式：`SelfCheck(tenantID)` 返回一个 `Report`，其中 `Invariants` 是各条检查的结果。
`InvariantResult.Checked` 是**检查了多少个对象**，不是发现了多少个问题——
它存在的唯一目的是区分「全查过且没问题」与「什么都没查」。

## I1：账户余额等于其流水增量之和

### 保证什么

对每个账户的每个资金桶（`Frozen` / `Available` / `Withdrawing` / `Withdrawn`），同时满足三条：

1. **求和一致**：账户上的值 == 该账户所有流水中对应桶的 `Delta*` 之和。
2. **尾部一致**：该账户**最后一条**流水的 `After*` 值 == 账户当前值。
3. **非负**：任何桶的值不小于 0。

### 为什么必须有第 2 条

只有第 1 条是不够的：如果有人把账户和流水**一起**改了，等式依然成立。
第 2 条检查的是「最后一条流水记录的当时结果，是否等于账户现在的样子」，
它抓的正是「账户被改了但流水没跟上」和「流水被改了但账户没跟上」这两种单边修改。

### 为什么桶要遍历而不是手写

`AllBuckets()` 是桶定义的**唯一来源**，并且有一条反射测试强制 `Account` 的每个 `Money`
字段都被归类为某个桶。手写 `if acct.Frozen != sum.Frozen || acct.Available != ...`
的写法会在新增资金字段时**静默漏掉它**——账目依然平，自检依然过，而新字段不在任何不变量里。

存储层的对账查询同样从 `AllBuckets()` 生成列名（ADR-041），理由相同。

### 由什么强制

- 写入路径：`LedgerEntry` 的 `After*` 由同一事务内的账本写入产生
- 检查路径：逐行 `checkLedgerConservation`，或集合式 `checkLedgerConservationReconciled`
- 测试：`invariant_test.go`、`store/sql/reconcile_test.go`（桶到列的映射必须完整）

### 不覆盖什么

- **不检查流水之间的因果**。两条流水的 `After*` 可以互相矛盾而各自与账户都不一致——
  本检查只看**最后一条**，中间的不一致可能被后来的正确流水掩盖。
- **不检查金额本身是否合理**。一笔把手数写错但自洽的佣金，I1 完全通过。

## I2：佣金与流水的关联，以及分配上界

检查名：`I2: commission ledger linkage and allocation cap`

### 保证什么

1. 每条佣金都有一条对应的**计提流水**（防「记了佣金但钱没动」）。
2. 每条计提流水都指向一条**存在的**佣金（防悬空引用）。
3. 计提流水的业务标识必须是合法数字（防标识被写坏后无法归属）。
4. 每个计算单元（订单 + 订单项）分配给各层级的佣金总额，不超过规则允许的上界。

### 第 1 条为什么必须直接枚举佣金

早期实现只从流水**反向**查找佣金，于是最需要被检测的形态——
「佣金记录写了，钱没动」——恰好查不出来，因为反向查找的前提就是流水存在。
第 1 条必须**正向枚举佣金**，这是它存在的全部意义。

### 不覆盖什么

- 检查的是**已分配总额**不超过上界，不检查分配**比例**是否符合当时的规则快照。
  规则快照记在佣金行上，用于审计与追溯，不用于自动判定。
- 上界基于佣金行自身记录的 `base_amount`，不重新计算订单金额是否真实。

## I3：冲正累加器、冲正链、状态与账户总额

检查名：`I3: reversal accumulator, state and account totals reconcile`

### 保证什么

I3 是三条不变量里检查项最多的一条，因为它要同时看住**佣金行、冲正链、状态机、账户累计**
四个地方。逐条列出：

**关于单条佣金**

1. `0 <= ReversedAmount <= Amount`——累加器越界即为损坏。
2. `FullyReversed()` 与状态一致：冲满的必须处于 `Reversed` 或 `Void`，
   没冲满的必须不在其中。这一条抓「累加器与状态机各说各话」。
3. 金额为负的佣金必须带 `reverse_of` 链接——负金额只应作为冲正存在。
4. `reverse_of` 指向的佣金必须**存在**，且必须是一条**计提**（不能冲正再冲正）。

**关于冲正明细与累加器**

5. `ReversedAmount` == 该佣金全部冲正明细之和。
6. 明细之和不得超过该佣金金额。

**关于账户累计**

7. `TotalEarned` == 该账户所有计提之和。
8. `TotalReversed` == 该账户所有冲正之和。

### 为什么需要它

`TotalEarned` / `TotalReversed` 这类**累计**字段曾经不在任何不变量里：
它们不影响「余额 == 流水之和」，所以 I1 抓不到；但它们是对外展示与对账报表的依据。
一个错误的累计值会一直错下去，且没有任何检查会报警。第 7、8 条就是为此而设。

第 2、3、4 条则是冲正链的结构完整性：冲正引入了「一条记录指向另一条记录」这个
I1/I2 都不涉及的维度，而指向关系正是最容易在并发与重试下写坏的东西。

修复分两层，缺一不可：

1. **结构层**——引入 `Bucket` 类型作为资金字段的唯一定义，反射测试强制每个 `Money`
   字段被归类。于是「新增字段但不进不变量」不再是靠人记得。
2. **检查层**——I3 显式校验上面八条。

只做第 2 层会在下次新增字段时重蹈覆辙；只做第 1 层则覆盖不了已经存在的累计字段。

### 不覆盖什么

- 不校验冲正**是否应该发生**（退款是否真实）。那取决于调用方传入的累计退款金额，
  库按「调用方说的是真的」处理，并把依据记进 `dist_refund` 凭证。
  这是刻意的边界：库不知道真实退款，只保证「按你给我的数字，账是自洽的」。
- 不校验 `ReversedAmount` 是否等于**应该**冲正的金额（例如按比例应冲多少），
  只校验它与明细自洽、且不越界。

## I4：提现单状态、冻结额与流水三者一致

检查名：`I4: withdrawal state, reservation and ledger agree`

### 保证什么

提现是这个库里**唯一一个状态声称了账户之外的事**的记录：`Paid` 意味着钱已经离开平台。
其它状态都是账户还能对质的承诺，而已出账的提现已经走了。因此要验两件事，且它们以不同方式失效：

**① 冻结额必须与桶对得上。** 账户的 `withdrawing` 桶**恰好**等于仍处于冻结状态的提现单之和。
这条抓的是**状态机看不见的那一类**：提现单被标记为已打款但没有移动钱——
这是一个**完全合法的状态迁移**，只有钱不见了。任何只看状态的检查都会放过它。

**② 流水必须佐证状态。** 冻结中的提现单必须有 `withdraw_hold` 流水，
已打款的要有 `withdraw_paid`，已驳回的要有 `withdraw_refund`。
状态存在而流水缺失，意味着库的两半对「发生了什么」说法不一致。

### 为什么 `Checked` 也数账户

一个没有任何提现单的租户，逐条检查提现单是**零项**——而那会让「查过了、没问题」
与「什么都没查」看起来一样。所以 I4 把**比对过的账户数**也计入 `Checked`：
正是这些账户证明了「桶是空的，因为没有东西冻结它」，而不是「查询什么都没找到」。

### 不覆盖什么

- **不校验收款账户的真实性。** 库看到的是调用方传来的脱敏字符串，不验证它属于谁。
- **不校验打款金额与渠道实际出账一致。** 库只知道渠道报告的结果。
  渠道说成功了而实际没出账，没有任何账本检查能发现——这是 `PayoutChannel` 幂等契约存在的原因。
- **不覆盖异步渠道。** 结果在调用时未知的渠道不在本次范围内（ADR-043）。

## 交叉不变量：这些检查共同依赖的前提

以下几点不属于任何单条不变量，但任一条被破坏都会让上面的检查失去意义：

| 前提 | 被破坏的后果 |
|---|---|
| 账本是**只追加**的 | 若流水可改，I1 的第 2 条就失去参照 |
| 财务字段**不可变** | 同上；生命周期字段可变但走版本 CAS |
| 金额是 `int64` 最小单位，不是浮点 | 浮点会让「相等」本身不可靠 |
| 幂等键唯一 | 重复投递会重复入账，而账目依然自洽 |

## 自检通过意味着什么

**意味着**：在上述前提成立、且检查覆盖的范围内，账目没有被发现不一致。

**不意味着**：

- 钱没有丢——金额算错但自洽的账，所有不变量都通过
- 业务规则正确——规则由可插拔层决定，库只保证账本对它保持一致
- 覆盖完整——`Report.Reconciled` 说明 I1 走的是哪条路径；
  I2 / I3 / I4 目前在**所有**存储下都是逐行的，它们的成本仍随数据量增长

最后一条是当前最实际的局限：做到集合式的只有 I1。
I2/I3 若要支撑同等规模，需要同样的下推处理。

> **I1 的两条路径必须给出同样的结论。** 集合式路径（`Reconciler`）与逐行路径调用
> 同一个判定函数，只在对账成本的来源上不同。存储层只回答「哪些账户可能不对」，
> **不判定**——否则不同存储下「什么算违规」就会漂移。
