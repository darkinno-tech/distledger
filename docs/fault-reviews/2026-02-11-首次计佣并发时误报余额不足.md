# 故障复盘：首次计佣并发时，向「正在加钱」的调用方返回了「余额不足」

## 基本信息

| 字段 | 内容 |
|------|------|
| 日期 | 2026-02-11 |
| 发现人 | 集成测试（偶发失败） |
| 严重程度 | P1-严重（错误信息误导调用方，且首次计佣在并发下大面积失败） |
| 影响范围 | `store/sql`（MySQL / PostgreSQL / SQLite 均受影响）；`Ledger.OnOrderPaid` 等所有走 `IncrementAccount` 的路径 |
| 关联提交 | 本次修复提交 |
| 相关代码位置 | `store/sql/write.go` `(*tx).IncrementAccount` |

## 1. 问题描述

### 1.1 问题场景

一个分销员**第一次**产生佣金时，账户行还不存在。多个订单几乎同时支付完成，并发进入 `OnOrderPaid`：

```
12 个 goroutine → OnOrderPaid(不同订单, 同一 buyer → 同一 agent)
                → IncrementAccount(+5.00)
```

每个事务都要经历「先 UPDATE（0 行）→ 查不到 → INSERT 建账户」这条路径。

### 1.2 具体表现

- 偶发：12 笔订单里有 1~2 笔直接失败，调用方拿到 error。
- 频次：单独跑 `TestEngineConcurrentOrdersToOneAgent/postgres` 时，10 次里约 6 次失败；但**单独跑一次经常通过**，看起来像「flaky test」。

### 1.3 错误信息

```
1 of 12 orders failed; concurrent writers must not conflict;
first error: distledger: insufficient balance for reversal:
applying {Key:t1/u3001 Frozen:5.00 Available:0.00 Withdrawing:0.00 Withdrawn:0.00
TotalEarned:5.00 TotalReversed:0.00 RequireNonNegative:false}
to account t1/u3001 would leave the [] bucket(s) negative
```

**注意这行错误的荒谬之处**：delta 是 **+5.00**，报出来的「会变负的桶」列表是 **空** ——
一个纯加钱的增量，被报成了「余额不足」。

## 2. 临时解决方案

无。此问题在集成测试阶段发现，未进入生产；没有采取止血措施，直接修复根因。

## 3. 根本原因分析

### 3.1 问题分析过程

**第 1 步：表象是「flaky test」。**
最初判断是测试不稳定。重跑两次通过，一度准备按「无关偶发」处理。

**第 2 步：把它当真实缺陷查，先让失败可诊断。**
原测试只统计失败**数量**，把 error 丢掉了：

```go
if err != nil {
    atomic.AddInt64(&failed, 1)
    return        // ← error 被丢弃
}
```

一个说不出原因的失败，是这次排查慢的真正原因。先改成记录首个 error 再重跑。

**第 3 步：拿到错误信息，发现错误「自相矛盾」。**
报的是 `ErrInsufficientBalance`，但这是一个**加钱**的操作，且 `RequireNonNegative:false` ——
根本不该有任何非负性检查。

**第 4 步：把 delta 打进错误信息，定位到具体分支。**
原错误只说「某个桶会变负」，不说 delta 是什么。补上 delta 与具体桶名后立刻看到
delta 是 `+5.00`、负数桶列表为**空**。

这说明 `IncrementAccount` 内部**误判**了分支：它认为「行存在 + 0 行受影响 = 守卫拒绝了这次更新」。

**第 5 步：还原真实的时序。**
`found == true` 并不等于「守卫拒绝了更新」。它还有第二种含义：

```
T1: UPDATE  (行还不存在)         → 0 行
        ← 此刻 T2 提交，账户行被创建
T1: SELECT  (行已存在)           → found = true
T1: 误判为「守卫拒绝」            → 返回 ErrInsufficientBalance  ❌
```

**「行在 UPDATE 与 SELECT 之间被创建」和「守卫拒绝」在代码里长得一模一样（0 行受影响），但需要完全相反的响应。**

### 3.2 直接原因

`IncrementAccount` 用「行存在」这一条信息去推断「守卫拒绝」，而这条信息不足以区分两种情形。

**相关代码位置**：`store/sql/write.go` `(*tx).IncrementAccount`

**修复前**：

```go
res, err := t.updateVersioned(ctx, update, b.vals)
if res.affected == 1 {
    acct, _, err := t.lookupAccount(ctx, delta.Key)
    return acct, err
}

_, found, err := t.lookupAccount(ctx, delta.Key)
if found {
    // ❌ 断言：行存在 ⇒ 守卫拒绝
    return distledger.Account{}, fmt.Errorf(
        "%w: applying %s would leave a bucket of account %s negative",
        distledger.ErrInsufficientBalance, delta.Key, delta.Key)
}
// 不存在 ⇒ 建账户
...
if !inserted {
    // ❌ 建账户也竞争失败 ⇒ 只能报冲突让调用方重试
    return distledger.Account{}, &distledger.ConflictError{...}
}
```

两处判断都建立在「我能分辨自己处在哪个竞态窗口」这个错误假设上。

### 3.3 根本原因

**设计层面**：把「一次 UPDATE 受影响 0 行」当成了**单一语义**，实际上它至少有三个来源：

1. 行不存在（需要 INSERT 建行）
2. 行存在但守卫条件不满足（真正的拒绝）
3. **行在语句执行后才出现**（UPDATE 只是「错过了」它，delta 一次都没应用）

第 3 种情况被完全遗漏。而增量运算是**可交换的**，所以第 3 种情况的正确处理是「再跑一次 UPDATE」，
不是报错。

**开发层面**：`IncrementAccount` 原有的单元测试全部是单线程的，第 3 种时序在单线程下不可构造。
并发语义只由集成测试覆盖，而集成测试把失败原因丢了。

**流程层面**：`ErrInsufficientBalance` 这个名字本身过度泛化（`errors.go:63` 定义为
`insufficient balance for reversal`），它被复用成了「账户增量被守卫拒绝」的通用错误，
于是「加钱被拒」这种不可能的输出没有被当成矛盾信号。

### 3.4 为什么没有提前发现

- **代码审查**：`increment` 的两条分支各自读起来都合理，问题只在跨语句时序上成立，静态阅读看不出来。
- **测试**：单线程测试无法构造该时序；唯一的并发测试**丢弃了 error**，只保留计数。
  更糟的是它**经常通过**（先到的事务建行了，后来者不再走这条路），所以看起来像 flaky 而不是 bug。
- **监控**：错误类型被复用，指标上无法区分「真实余额不足」与「误判」。

## 4. 解决方案

### 4.1 根本解决方案

**修改文件**：`store/sql/write.go`

把「0 行受影响」的三种来源显式分开，并让两个竞态共用同一个「重试」响应：

```go
// 最多两趟。第一趟把增量应用到已存在的账户，或创建账户；
// 输掉创建竞争就再来一趟，因为此时赢家的行已经存在，同一条 UPDATE 就能应用。
// 增量是可交换的，所以「重新应用」不等于「应用两次」。
for attempt := 0; ; attempt++ {
    res, err := t.updateVersioned(ctx, update, b.vals)
    if res.affected == 1 { ... return }

    acct, found, err := t.lookupAccount(ctx, delta.Key)
    if found {
        // 0 行受影响且行存在，有两种原因，需要相反的响应：
        //   守卫拒绝 → 调用方要的答案
        //   UPDATE 执行后行才被创建 → 增量一次都没应用，必须重试
        // 靠「这次增量是否真的会把某个桶压成负数」区分二者。
        after, err := delta.Apply(acct)
        if bad := after.NegativeBuckets(); delta.RequireNonNegative && len(bad) > 0 {
            return ..., fmt.Errorf("%w: applying %+v to account %s would leave the %v bucket negative",
                distledger.ErrInsufficientBalance, delta, delta.Key, bad[0])
        }
        if attempt == 0 { continue }          // ← 关键：只是错过了行，再来一次
        return ..., &distledger.ConflictError{...}
    }
    // 不存在 ⇒ 建账户；建失败（输掉竞争）时 attempt==0 也 continue
}
```

**为什么选这个方案**：

- **对比「调用方重试」**：报 `ConflictError` 让上层重试也能最终成功，但这是把库内部可以自行消解的竞态
  外推给每一个调用方，且首次计佣在并发下会大面积失败（12 笔里错 5 笔）。**库应该在自己能解决的地方解决。**
- **对比「先 INSERT 再 UPDATE，用 ON CONFLICT DO UPDATE」**：`ON CONFLICT DO UPDATE` 会**覆盖**而非累加，
  要写成 `SET x = x + excluded.x` 才正确，而 MySQL 的 `ON DUPLICATE KEY UPDATE` 语法不同、
  SQLite 又是第三种。这会把「方言差异」从 DDL 扩散到热路径 SQL。放弃。

### 4.2 影响范围评估

- 仅改动 `IncrementAccount` 内部的语句编排，**端口签名与语义不变**。
- 最坏情况由「1 条 UPDATE + 1 次 SELECT + 1 条 INSERT」变为「2 条 UPDATE + 2 次 SELECT + 1 条 INSERT」，
  只发生在**首次计佣且发生竞争**时；常规路径（行已存在）仍是**单条 UPDATE**。
- store 的重试循环不变，`ConflictError` 仍是最后兜底。

实测：`TestEngineConcurrentOrdersToOneAgent` 连续 25 次全部通过（修复前 10 次里失败 6 次）。

## 5. 预防措施

### 5.1 代码层面

- [x] 0 行受影响的分支必须枚举**所有**来源，不能只处理「行不存在」。
- [x] 错误信息必须携带足够定位的上下文：本次修复把 delta 与具体桶名写进了错误，
      否则「报错的 delta 到底是正是负」还得靠猜。
- [x] 幂等/可交换的写操作，输掉竞态后应「自己重试」而非上报。

### 5.2 测试层面

- [x] **禁止丢弃 error**：并发测试必须保留首个错误并输出。仅统计失败数量会让排查从「看一眼日志」
      变成「反复重跑碰运气」。
- [x] 并发测试要**构造首次写入的竞态**（账户行预先不存在），并在无数据库依赖的层留下可复现的探针。
- [ ] 待补：`store/memory` 侧无法复现该时序（有全局锁），因此这条语义只由集成测试覆盖——
      在 `integration/contract_test.go` 中固定该场景，避免它只存在于一个「顺手写的」引擎测试里。

### 5.3 监控层面

- [ ] `ErrInsufficientBalance` 应按「被拒的桶」与操作类型打标签，否则无法从指标上区分误判与真实不足。

### 5.4 流程/规范层面

- [x] 已写入本复盘库。
- [x] 同类原则补入 `docs/design-decisions.md`：**「一次语句的 0 行受影响」不是单一语义**。

## 6. 经验总结（一句话）

> 把「0 行受影响」当成单一语义，是最容易写出「加钱被报成余额不足」的地方——
> **行存在 + 0 行受影响**必须继续区分「守卫拒绝」与「语句执行后行才出现」，
> 而后者对一个可交换的增量来说，正确答案是重试，不是报错。

## 附：为什么这条教训在「幂等 + 并发 + 乐观锁」的库里格外重要

本库的核心承诺是「同一事件重复投递结果一致」。`IncrementAccount` 是唯一一处**不做版本 CAS**
的写入（ADR-037 刻意为之：账户余额走原子增量，避免热点行读改写）。

代价是：它把「我在哪个竞态窗口里」这个判断责任完全交给了自己的分支逻辑。
版本 CAS 的写入天然安全（版本不匹配就是明确的冲突），而增量写入没有这个信号，
**必须靠「重新读到的状态是否真的解释得通」来推断**。这是 ADR-037 用性能和热点换取的成本，
本故障就是该成本的一次具体兑现。
