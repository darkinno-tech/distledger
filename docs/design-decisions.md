## ADR-001 只做账务内核，不做分销系统

**背景**
调研结论：Go 生态没有可直接用的分销库；市面开源分销（SparkShop / Open-Shop 等）都是 PHP/Java 电商系统的内置模块；Go 唯一代表 Golershop 的开源版摘掉了 `internal/logic` 与路由绑定，只剩表结构与接口声明。

**决策**
`distledger` 只做**资金账务内核**，不做完整分销系统。

**理由**
分销的业务规则是无限长尾（门槛、层级、费率、关系绑定方式每家都不同），但资金账务流对所有人完全一样：

```
订单归属 → 按规则算佣金 → 冻结 → 到期可提现 → 退款扣回 → 出金
```

规则在客户手里（长尾），责任在库里（钱不能错）。把两头都做进库，必然长成谁都不好用的巨无霸。

**代价**
不能开箱即用地"一键拥有分销系统"；使用者仍需自己写推广链接、后台、UI。

**被否决的替代方案**
- ❌ 做完整分销系统 → 与市面 PHP/Java 商城正面竞争，且 Go 生态无此需求缺口
- ❌ 做 open core（开源版裁剪、商业版完整）→ 违背本项目"非商业"定位，且伤害信任

## ADR-002 切分线：钱"流向" vs 钱"数值"

**背景**
常见说法是"内核做资金账务、规则做业务策略"。但这个切分**太粗**：像"什么时候算数"（支付即结算？确认收货结算？）看起来是业务规则，实际是状态机的一部分。一旦把它放进规则层，就会有人自定义出"支付即确佣"，然后把退款跑单的锅甩给库。

**决策**
切分判据只有一句：

> **能改变"钱流向"的决策 → 内核；只改变"钱数值"的决策 → 规则层。**
> **规则层永远不许修改状态。**

| 决策 | 归属 |
|---|---|
| 何时确佣/解冻/冲正 | 🔒 内核 |
| 退款怎么扣回、是否允许负余额 | 🔒 内核 |
| 幂等、事务边界、余额守恒 | 🔒 内核 |
| 算多少（比例/固定/阶梯） | 🔌 规则层（只输出数字） |
| 够不够格（门槛/审核/等级） | 🔌 规则层（只输出布尔） |
| 几级（1/2/3） | 🔌 规则层（只输出层级数） |
| 绑不绑、绑多久 | 🔌 规则层（只输出关系与有效期） |

**代价**
`Calculator` 接口的表达能力受限（不能自定义状态迁移），部分特殊诉求无法满足。

**被否决的替代方案**
- ❌ 把状态机也做成可插拔 → 每人一套状态机 = 库无法保证任何不变量 = 库失去存在意义

## ADR-003 金额用 `int64` 分，费率用万分比

**背景**
Golershop 的 `pay_distribution_commission` 使用 `decimal(15,2)`，Go 侧对应 `float64`。浮点参与金额运算会产生累积误差；`decimal` 在 Go 里需要第三方库（违反零依赖原则）。

**决策**
- 一切金额用 **`int64` 最小货币单位（分）**
- 一切费率用 **`int` 万分比（basis point）**，5% = `500` bp
- 全程**禁止** `float64` 参与金额运算

**理由**
整数运算精确、可比较、可索引、无依赖。费率用 bp 使"5%"变成整数 `500`，且能表达 0.01% 的粒度。

**代价**
对外展示需要除以 100 / 10000；与外部系统（多为 decimal 元）交互时需要显式转换，转换函数必须集中提供。

**被否决的替代方案**
- ❌ `float64` → 精度事故
- ❌ `shopspring/decimal` → 违反零依赖原则
- ❌ 金额元 + 小数字段 → 运算复杂度更高

## ADR-004 佣金明细不可变 + 复式流水

**背景**
常见实现把"佣金明细"直接当作账。但**明细不是账**：明细只回答"这笔钱从哪来"，不回答"账户余额怎么变成现在这样"。Golershop 的 `trade_distribution_generated_commission` 注释写着"记录不变，如果关系更变，则增加其它记录"——这印证了不可变思路，但它缺少独立的资金流水表。

**决策**
1. 佣金单**只追加不修改**；冲正通过**新增负额记录** + `reverse_of` 指向原记录
2. 独立 `dist_ledger` 表记录每一次余额变动（复式），含变动前后余额

**理由**
- 可审计：任何人改不了历史
- 可对账：`SUM(ledger.delta_*) == account.*` 是可验证的不变量
- 可解释：每一分钱都能反推来源

**代价**
数据量增长；聚合查询需要 `SUM`；账户表需要冗余维护（用乐观锁 + 事务保证一致）。

**被否决的替代方案**
- ❌ 直接 `UPDATE commission SET amount = 0` 表示退款 → 历史不可追溯，无法审计
- ❌ 只有明细没有流水 → 对账时无法定位差异

## ADR-005 冻结期在入账时快照

**背景**
Golershop（及多数实现）用**全局配置** `withdraw_received_day`（客户确认收货后 N 天可提现）+ 订单的 `uo_receivetime`，在**查询时推导**可提现时点。

这意味着：**运营改一次全局配置，所有历史订单的可提现时点随之改变** —— 已经承诺给分销员的到账时间被单方面改动，是纠纷与投诉的高发点，且无法自证当时的规则。

**决策**
佣金入账时把 `freeze_days` **快照**进佣金单，并计算出 `available_at = 收货时间 + freeze_days`。此后任何配置变更都不影响已入账记录。

**理由**
"当时的规则决定当时的钱"是账务系统的基本要求。快照让每笔佣金的解释独立于当前配置。

**代价**
每笔佣金多两个字段；配置变更需明确"只对新订单生效"的产品语义。

**被否决的替代方案**
- ❌ 查询时推导（Golershop 做法）→ 历史被污染
- ❌ 为每次配置变更做版本化推导 → 复杂度高，且 `available_at` 仍是算出来的，不是事实

## ADR-006 绑定/归因独立成表

**背景**
Golershop 把分销归属**冗余在订单表**上（`order_info.DistributorUserId`）。这种做法对查询友好，但绑定关系本身（谁绑了谁、什么时候绑的、绑多久、是否有效）无处存放。

**决策**
独立 `dist_binding` 表存放绑定关系；订单表**可选**冗余归属字段（作为查询加速，不作为事实来源）。

**理由**
"换绑冷静期""客户保护期""关系有效期""老客不抢"这些规则都需要**修改绑定关系本身**，而不是修改某一笔订单。塞进订单表就改不了。

**代价**
多一张表 + 一次查询；订单查询若要带归属信息需要 join（或冗余）。

**被否决的替代方案**
- ❌ 只存订单冗余字段 → 无法表达绑定的时间维度
- ❌ 绑定关系塞进 `dist_agent.parent_id` → 只能表达"永久上级"，无法表达"这笔订单归属谁"

## ADR-007 双 `Store`：`memory` + `mysql`

**背景**
开发者试用一个库的最大摩擦是**环境准备**：装 MySQL、建库、建表、配连接。让开发者在看到第一个佣金数字之前先做这些，转化率必然极低。

**决策**
同时维护两套 `Store` 实现，**接口完全同构**：

- `store/memory` —— 内存实现，用于首次体验与单元测试
- `store/mysql` —— 生产实现，`database/sql` 裸写 SQL

**理由**
`memory` 把所有时间驱动测试（冻结期、结算、超时）变成"注入时间 + 立即断言"，无需 `sleep`，无需数据库。它同时是**最快的文档**——`examples/01` 30 秒跑通。

**代价**
维护两套实现，存在行为漂移风险 → 用**同一套契约测试（contract test）跑在两个 store 上**来缓解。

**被否决的替代方案**
- ❌ 只用 MySQL → 首次体验门槛过高
- ❌ 只用 SQLite（`modernc.org/sqlite`）→ 引入第三方依赖，违反零依赖原则
- ❌ 只用内存 mock → 生产不可用

## ADR-008 幂等键由库生成

**背景**
订单状态回调重复投递是**常态**（支付回调重试、MQ at-least-once、用户重复点击）。多数实现把去重责任推给调用方，结果就是有人忘了，佣金算两遍。

**决策**
库内部从事件字段**派生** `idem_key`（订单 ID + 明细 ID + 分销员 + 层级 + 业务类型），并落 `UNIQUE(tenant_id, idem_key)` 约束。重复投递是 no-op。

**理由**
**开发者应该可以无脑重试。** 把防重放在库里，是唯一能保证"所有用户都不会漏"的位置。

**代价**
派生规则必须稳定（一旦改变需考虑兼容）；某些自定义场景需要允许调用方覆盖 `idem_key`。

**被否决的替代方案**
- ❌ 纯代码层 `if exists` 判断 → 并发下必然穿透，且每人都要写一遍
- ❌ 交给调用方生成 → 等于没做

## ADR-009 单一心跳 `Maintain()`

**背景**
一个分销内核内部至少有三类时间驱动逻辑：冻结到期结算、提现单超时、订单关闭清理。若把这些暴露成三个函数，用户需要理解内部状态机阶段，还要为每个挂一个 cron。

**决策**
对外只暴露 **一个** `Maintain(ctx, now)`，内部按序推进所有时间驱动状态，返回汇总结果。

**理由**
**用户不该理解库的内部阶段。** 一个函数挂一次 cron，接入成本从"理解三个阶段"降到"抄一行"。

**代价**
无法单独调度某一类任务（如只想跑结算）；单次 `Maintain` 耗时可能较长 → 通过 `MaintainOption`（如 `WithPhase`）作为高级用法保留，但不作为默认入口。

**被否决的替代方案**
- ❌ 暴露 `Settle()/Expire()/Cleanup()` → 用户必然漏挂其中一个
- ❌ 库内自建 goroutine 定时器 → 与用户的调度体系冲突，且无法控制启停

## ADR-010 默认不发钱

**背景**
库的默认值决定事故形态。若默认费率为 5%，一个配置不完整的接入会**真的发钱**；若默认费率为 0%，同一个接入只会"没发钱"。

**决策**
`DefaultRules()` 的费率为 `[0, 0]`，默认 2 级，默认 `AutoPayout=false`（人工审核）。

**理由**
**配置麻烦可以忍，默认错发钱不能忍。** 显式配置费率这一步，本身也是对运营的"确认动作"——它强制用户思考"我到底要分多少"。

**代价**
Quickstart 必须显式写 `RateBP`，否则看到 0 元佣金会困惑。缓解：example 里显式配置，并在 README 说明原因。

**被否决的替代方案**
- ❌ 默认 5%/3% → 任何默认值都是错的，且事故不可逆
- ❌ 不配置直接返回错误 → 首次体验太硬，且无法演示链路

## ADR-011 层级硬上限 3

**背景**
《禁止传销条例》与《刑法》第 224 条之一对分销层级有明确约束。Golershop 通过配置项 `plantform_fx_cps_rate_2_enable` / `_3_enable` 让运营可以关闭二级/三级——这是**合规退让装置**，说明成熟产品也把层级当作风险开关。

**决策**
`Levels` 配置项**硬编码上限为 3**，`Rules` 校验时超出直接返回错误。**不提供**任何按"拉人头/注册人数"计酬的能力。

**理由**
合规在工程上不能只靠"少配一级"。把上限写进代码，防止运营误配第 4 级，也防止使用者无意中踩线。

**代价**
确实存在合法的多级经销场景无法覆盖 → 明确写入 Non-Goals，使用者可自行实现 `Calculator`，但库不为此提供便利。

**被否决的替代方案**
- ❌ 完全由配置决定层级上限 → 一次误配就是法律风险
- ❌ 提供"注册佣金/拉新奖励"内置支持 → 这正是合规红线（Golershop 的 `commission_reg_amount_*` 就实现了，我们刻意不做）

## ADR-012 禁止 codegen 与反射

**背景**
许多 Go 框架（含 GoFrame）依赖代码生成与反射注册（`group.Bind(...)`）。

**决策**
不生成代码、不用反射做注册、不用全局单例。规则、Store、Channel 全部显式传入 `Config`。

**理由**
- **可调试**：调用栈不会断在反射里
- **可静态分析**：`go vet`、IDE 跳转、依赖图都工作正常
- **可预测**：没有"为什么这个 handler 没注册"这类问题（Golershop 开源版正是靠摘除 `group.Bind` 列表来裁剪功能——这种隐式绑定对使用者极不友好）

**代价**
接入时需要多写几行显式装配（约 5 行）。

**被否决的替代方案**
- ❌ `init()` 自动注册 → 隐式全局状态，测试无法隔离
- ❌ 代码生成 → 增加构建复杂度，且生成物容易与源码漂移

## ADR-013 不做隐式建表

**背景**
`AutoMigrateOnInit()` 这类"便捷"设计很常见。

**决策**
建表必须是**显式**调用 `mysqlstore.Migrate(ctx, db)`，同时提供 `schema.sql` 供迁移工具/手工执行。

**理由**
生产环境的隐式 DDL 是灾难：应用账号不应有 DDL 权限、变更无法审计、灰度/回滚无法控制、多实例同时启动可能并发建表。

**代价**
接入多一步（约 1 行）。

**被否决的替代方案**
- ❌ 首次连接自动建表 → 生产事故
- ❌ 内置完整迁移框架 → 重复造轮子且与用户的迁移工具冲突

## ADR-014 MIT 许可与"不商用"的澄清

**背景**
需求表述为"开源项目、不商用、MIT 协议"。但 **MIT 协议明确授予任何人商业使用权**——"不商用"与 MIT 之间存在字面矛盾，若不澄清会造成两种误读。

**决策**
采用 **MIT**，并在 README 与 PRD 中显式澄清：

> 本项目的"非商业"指**项目发起方不以盈利为目的**（不做商业版、不卖授权、不做 open core 裁剪），**不是限制使用者商用**。

**理由**
- 选 MIT 是为了最大化采用率与信任（无 copyleft 传染、企业法务无障碍）
- 若真的想"禁止他人商用"，必须改用 PolyForm Noncommercial / BSL 等**非 OSI 许可**，那就**不再是开源项目**

**代价**
无法通过许可获得任何商业回报（这是刻意的，也是定位的一部分）。

**被否决的替代方案**
- ❌ GPL/LGPL → 对企业采用有阻碍，与"最大化复用"目标相悖
- ❌ PolyForm Noncommercial → 不是开源许可，与"开源项目"定位冲突
- ❌ 参考 Golershop 的 open core（README 声明"非商业授权"但 LICENSE 文件是 LGPL-3.0，**自相矛盾**）→ 这种许可混乱会直接劝退使用者，我们刻意避免

## ADR-015 `SelfCheck()` 自检

**背景**
接入一个账务库时，最常见的失败不是"报错"，而是**静默的错误**：表没建全、`Maintain` 没挂、配置不自洽、余额与流水已经不一致。

**决策**
提供 `SelfCheck(ctx, tenantID) (Report, error)`，一次调用返回结构化报告：

- **Schema 检查**：7 张表是否全部存在，字段是否匹配
- **不变量检查**：`I1` 余额 == 流水和；`I2` 分佣总额 ≤ 可分配上限；`I3` 净佣金 ≥ 0
- **配置检查**：费率是否配置、层级是否超限、冻结期是否合理
- **计数统计**：各状态的佣金单/提现单数量（便于发现"卡住"的数据）

**理由**
**它是接入排障的唯一入口。** 有它，使用者能在 1 分钟内自诊 90% 的接入问题，而不必来提 issue。

**代价**
需要额外实现检查逻辑，且检查逻辑本身要保持与表结构同步。

**被否决的替代方案**
- ❌ 只提供日志 → 静默错误不会被发现
- ❌ 只提供 `HealthCheck` 返回 bool → 无法定位问题

## 附：从 Golershop 学到什么（反面与正面）

调研 [Golershop](https://github.com/shsuishang/golershop)（Go + GoFrame 电商系统）得出的结论，直接影响了本项目的多个 ADR：

### 值得借鉴（正面）

| Golershop 的做法 | 我们采纳为 |
|---|---|
| 订单表冗余 `DistributorUserId` / `OrderFxIsSettlemented` / `OrderFxSettlementTime` | ADR-006：订单表**可选冗余**归属，但独立 `dist_binding` 存事实 |
| `trade_distribution_generated_commission` 注释"记录不变，如果关系更变，则增加其它记录" | ADR-004：账本不可变 |
| `pay_distribution_commission` 聚合表带 `version` 字段（乐观锁） | ADR-004：账户表用 `version` 做乐观锁 |
| 配置项 `plantform_fx_cps_rate_2_enable` / `_3_enable`（每级独立开关） | ADR-011：层级是风险开关（我们进一步硬编码上限） |
| `pay_consume_withdraw` 提现表的字段设计（手续费/银行流水/状态机/关联退款单） | `dist_withdraw` 表设计 |

### 刻意规避（反面）

| Golershop 的做法 | 问题 | 我们的做法 |
|---|---|---|
| **open core 切片**：保留 api/entity/dao/sql，摘掉 `internal/logic` 与 `group.Bind` 路由绑定 | 能编译、能启动、后台有菜单，但调用时才炸；使用者无法判断哪些功能真实存在 | 本项目**不做 open core**（ADR-001），所有宣称的能力都必须有实现 |
| 冻结期用全局配置**查询时推导** | 改配置污染历史订单 | ADR-005：入账时快照 |
| 金额 `decimal(15,2)` / Go 侧 `float64` | 浮点误差 | ADR-003：`int64` 分 |
| 字段重载：`user_is_da` 注释"0-否;1-是**为区Id**" | 同一字段既当布尔又当区域 ID，可读性与正确性双输 | 显式拆字段 |
| 类型与语义不一致：`uo_active tinyint(3)` 注释 `(BOOL)` | Go 侧是 `bool`，容易错 | 类型即语义 |
| `commission_reg_amount_*`（注册佣金）、`commission_click_amount_*`（流量佣金） | **按拉新注册/点击计酬，正是合规红线** | ADR-011：**刻意不提供** |
| README 声明"非商业授权"，但 `LICENSE` 文件是 LGPL-3.0 | 许可自相矛盾，商用前无法判断 | ADR-014：许可表述唯一且明确 |
