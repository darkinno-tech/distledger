## ADR-001 只做账务内核，不做分销系统

**背景**
调研结论：Go 生态没有可直接用的分销库；市面开源分销（SparkShop / Open-Shop 等）都是 PHP/Java 电商系统的内置模块；Go 唯一代表 Golershop 的开源版摘掉了 `internal/logic` 与路由绑定，只剩表结构与接口声明。

**决策**
`distledger` 只做**资金账务内核**，不做完整分销系统。

**理由**
分销的业务规则是无限长尾（门槛、层级、费率、关系绑定方式每家都不同），但资金账务流对所有人完全一样：

```
订单归属 → 按规则算佣金 → 冻结 → 到期可提现 → 退款扣回 → 出金
```

规则在客户手里（长尾），责任在库里（钱不能错）。把两头都做进库，必然长成谁都不好用的巨无霸。

**代价**
不能开箱即用地"一键拥有分销系统"；使用者仍需自己写推广链接、后台、UI。

**被否决的替代方案**
- ❌ 做完整分销系统 → 与市面 PHP/Java 商城正面竞争，且 Go 生态无此需求缺口
- ❌ 做 open core（开源版裁剪、商业版完整）→ 违背本项目"非商业"定位，且伤害信任

## ADR-002 切分线：钱"流向" vs 钱"数值"

**背景**
常见说法是"内核做资金账务、规则做业务策略"。但这个切分**太粗**：像"什么时候算数"（支付即结算？确认收货结算？）看起来是业务规则，实际是状态机的一部分。一旦把它放进规则层，就会有人自定义出"支付即确佣"，然后把退款跑单的锅甩给库。

**决策**
切分判据只有一句：

> **能改变"钱流向"的决策 → 内核；只改变"钱数值"的决策 → 规则层。**
> **规则层永远不许修改状态。**

| 决策 | 归属 |
|---|---|
| 何时确佣/解冻/冲正 | 🔒 内核 |
| 退款怎么扣回、是否允许负余额 | 🔒 内核 |
| 幂等、事务边界、余额守恒 | 🔒 内核 |
| 算多少（比例/固定/阶梯） | 🔌 规则层（只输出数字） |
| 够不够格（门槛/审核/等级） | 🔌 规则层（只输出布尔） |
| 几级（1/2/3） | 🔌 规则层（只输出层级数） |
| 绑不绑、绑多久 | 🔌 规则层（只输出关系与有效期） |

**代价**
`Calculator` 接口的表达能力受限（不能自定义状态迁移），部分特殊诉求无法满足。

**被否决的替代方案**
- ❌ 把状态机也做成可插拔 → 每人一套状态机 = 库无法保证任何不变量 = 库失去存在意义

## ADR-003 金额用 `int64` 分，费率用万分比

**背景**
Golershop 的 `pay_distribution_commission` 使用 `decimal(15,2)`，Go 侧对应 `float64`。浮点参与金额运算会产生累积误差；`decimal` 在 Go 里需要第三方库（违反零依赖原则）。

**决策**
- 一切金额用 **`int64` 最小货币单位（分）**
- 一切费率用 **`int` 万分比（basis point）**，5% = `500` bp
- 全程**禁止** `float64` 参与金额运算

**理由**
整数运算精确、可比较、可索引、无依赖。费率用 bp 使"5%"变成整数 `500`，且能表达 0.01% 的粒度。

**代价**
对外展示需要除以 100 / 10000；与外部系统（多为 decimal 元）交互时需要显式转换，转换函数必须集中提供。

**被否决的替代方案**
- ❌ `float64` → 精度事故
- ❌ `shopspring/decimal` → 违反零依赖原则
- ❌ 金额元 + 小数字段 → 运算复杂度更高

## ADR-004 佣金明细不可变 + 复式流水

**背景**
常见实现把"佣金明细"直接当作账。但**明细不是账**：明细只回答"这笔钱从哪来"，不回答"账户余额怎么变成现在这样"。Golershop 的 `trade_distribution_generated_commission` 注释写着"记录不变，如果关系更变，则增加其它记录"——这印证了不可变思路，但它缺少独立的资金流水表。

**决策**
1. 佣金单**只追加不修改**；冲正通过**新增负额记录** + `reverse_of` 指向原记录
2. 独立 `dist_ledger` 表记录每一次余额变动（复式），含变动前后余额

**理由**
- 可审计：任何人改不了历史
- 可对账：`SUM(ledger.delta_*) == account.*` 是可验证的不变量
- 可解释：每一分钱都能反推来源

**代价**
数据量增长；聚合查询需要 `SUM`；账户表需要冗余维护（用乐观锁 + 事务保证一致）。

**被否决的替代方案**
- ❌ 直接 `UPDATE commission SET amount = 0` 表示退款 → 历史不可追溯，无法审计
- ❌ 只有明细没有流水 → 对账时无法定位差异

## ADR-005 冻结期在入账时快照

**背景**
Golershop（及多数实现）用**全局配置** `withdraw_received_day`（客户确认收货后 N 天可提现）+ 订单的 `uo_receivetime`，在**查询时推导**可提现时点。

这意味着：**运营改一次全局配置，所有历史订单的可提现时点随之改变** —— 已经承诺给分销员的到账时间被单方面改动，是纠纷与投诉的高发点，且无法自证当时的规则。

**决策**
佣金入账时把 `freeze_days` **快照**进佣金单，并计算出 `available_at = 收货时间 + freeze_days`。此后任何配置变更都不影响已入账记录。

**理由**
"当时的规则决定当时的钱"是账务系统的基本要求。快照让每笔佣金的解释独立于当前配置。

**代价**
每笔佣金多两个字段；配置变更需明确"只对新订单生效"的产品语义。

**被否决的替代方案**
- ❌ 查询时推导（Golershop 做法）→ 历史被污染
- ❌ 为每次配置变更做版本化推导 → 复杂度高，且 `available_at` 仍是算出来的，不是事实

## ADR-006 绑定/归因独立成表

**背景**
Golershop 把分销归属**冗余在订单表**上（`order_info.DistributorUserId`）。这种做法对查询友好，但绑定关系本身（谁绑了谁、什么时候绑的、绑多久、是否有效）无处存放。

**决策**
独立 `dist_binding` 表存放绑定关系；订单表**可选**冗余归属字段（作为查询加速，不作为事实来源）。

**理由**
"换绑冷静期""客户保护期""关系有效期""老客不抢"这些规则都需要**修改绑定关系本身**，而不是修改某一笔订单。塞进订单表就改不了。

**代价**
多一张表 + 一次查询；订单查询若要带归属信息需要 join（或冗余）。

**被否决的替代方案**
- ❌ 只存订单冗余字段 → 无法表达绑定的时间维度
- ❌ 绑定关系塞进 `dist_agent.parent_id` → 只能表达"永久上级"，无法表达"这笔订单归属谁"

## ADR-007 双 `Store`：`memory` + `mysql`

**背景**
开发者试用一个库的最大摩擦是**环境准备**：装 MySQL、建库、建表、配连接。让开发者在看到第一个佣金数字之前先做这些，转化率必然极低。

**决策**
同时维护两套 `Store` 实现，**接口完全同构**：

- `store/memory` —— 内存实现，用于首次体验与单元测试
- `store/mysql` —— 生产实现，`database/sql` 裸写 SQL

**理由**
`memory` 把所有时间驱动测试（冻结期、结算、超时）变成"注入时间 + 立即断言"，无需 `sleep`，无需数据库。它同时是**最快的文档**——`examples/01` 30 秒跑通。

**代价**
维护两套实现，存在行为漂移风险 → 用**同一套契约测试（contract test）跑在两个 store 上**来缓解。

**被否决的替代方案**
- ❌ 只用 MySQL → 首次体验门槛过高
- ❌ 只用 SQLite（`modernc.org/sqlite`）→ 引入第三方依赖，违反零依赖原则
- ❌ 只用内存 mock → 生产不可用

## ADR-008 幂等键由库生成

**背景**
订单状态回调重复投递是**常态**（支付回调重试、MQ at-least-once、用户重复点击）。多数实现把去重责任推给调用方，结果就是有人忘了，佣金算两遍。

**决策**
库内部从事件字段**派生** `idem_key`（订单 ID + 明细 ID + 分销员 + 层级 + 业务类型），并落 `UNIQUE(tenant_id, idem_key)` 约束。重复投递是 no-op。

**理由**
**开发者应该可以无脑重试。** 把防重放在库里，是唯一能保证"所有用户都不会漏"的位置。

**代价**
派生规则必须稳定（一旦改变需考虑兼容）；某些自定义场景需要允许调用方覆盖 `idem_key`。

**被否决的替代方案**
- ❌ 纯代码层 `if exists` 判断 → 并发下必然穿透，且每人都要写一遍
- ❌ 交给调用方生成 → 等于没做

## ADR-009 单一心跳 `Maintain()`

**背景**
一个分销内核内部至少有三类时间驱动逻辑：冻结到期结算、提现单超时、订单关闭清理。若把这些暴露成三个函数，用户需要理解内部状态机阶段，还要为每个挂一个 cron。

**决策**
对外只暴露 **一个** `Maintain(ctx, now)`，内部按序推进所有时间驱动状态，返回汇总结果。

**理由**
**用户不该理解库的内部阶段。** 一个函数挂一次 cron，接入成本从"理解三个阶段"降到"抄一行"。

**代价**
无法单独调度某一类任务（如只想跑结算）；单次 `Maintain` 耗时可能较长 → 通过 `MaintainOption`（如 `WithPhase`）作为高级用法保留，但不作为默认入口。

**被否决的替代方案**
- ❌ 暴露 `Settle()/Expire()/Cleanup()` → 用户必然漏挂其中一个
- ❌ 库内自建 goroutine 定时器 → 与用户的调度体系冲突，且无法控制启停

## ADR-010 默认不发钱

**背景**
库的默认值决定事故形态。若默认费率为 5%，一个配置不完整的接入会**真的发钱**；若默认费率为 0%，同一个接入只会"没发钱"。

**决策**
`DefaultRules()` 的费率为 `[0, 0]`，默认 2 级，默认 `AutoPayout=false`（人工审核）。

**理由**
**配置麻烦可以忍，默认错发钱不能忍。** 显式配置费率这一步，本身也是对运营的"确认动作"——它强制用户思考"我到底要分多少"。

**代价**
Quickstart 必须显式写 `RateBP`，否则看到 0 元佣金会困惑。缓解：example 里显式配置，并在 README 说明原因。

**被否决的替代方案**
- ❌ 默认 5%/3% → 任何默认值都是错的，且事故不可逆
- ❌ 不配置直接返回错误 → 首次体验太硬，且无法演示链路

## ADR-011 层级硬上限 3

**背景**
《禁止传销条例》与《刑法》第 224 条之一对分销层级有明确约束。Golershop 通过配置项 `plantform_fx_cps_rate_2_enable` / `_3_enable` 让运营可以关闭二级/三级——这是**合规退让装置**，说明成熟产品也把层级当作风险开关。

**决策**
`Levels` 配置项**硬编码上限为 3**，`Rules` 校验时超出直接返回错误。**不提供**任何按"拉人头/注册人数"计酬的能力。

**理由**
合规在工程上不能只靠"少配一级"。把上限写进代码，防止运营误配第 4 级，也防止使用者无意中踩线。

**代价**
确实存在合法的多级经销场景无法覆盖 → 明确写入 Non-Goals，使用者可自行实现 `Calculator`，但库不为此提供便利。

**被否决的替代方案**
- ❌ 完全由配置决定层级上限 → 一次误配就是法律风险
- ❌ 提供"注册佣金/拉新奖励"内置支持 → 这正是合规红线（Golershop 的 `commission_reg_amount_*` 就实现了，我们刻意不做）

## ADR-012 禁止 codegen 与反射

**背景**
许多 Go 框架（含 GoFrame）依赖代码生成与反射注册（`group.Bind(...)`）。

**决策**
不生成代码、不用反射做注册、不用全局单例。规则、Store、Channel 全部显式传入 `Config`。

**理由**
- **可调试**：调用栈不会断在反射里
- **可静态分析**：`go vet`、IDE 跳转、依赖图都工作正常
- **可预测**：没有"为什么这个 handler 没注册"这类问题（Golershop 开源版正是靠摘除 `group.Bind` 列表来裁剪功能——这种隐式绑定对使用者极不友好）

**代价**
接入时需要多写几行显式装配（约 5 行）。

**被否决的替代方案**
- ❌ `init()` 自动注册 → 隐式全局状态，测试无法隔离
- ❌ 代码生成 → 增加构建复杂度，且生成物容易与源码漂移

## ADR-013 不做隐式建表

**背景**
`AutoMigrateOnInit()` 这类"便捷"设计很常见。

**决策**
建表必须是**显式**调用 `mysqlstore.Migrate(ctx, db)`，同时提供 `schema.sql` 供迁移工具/手工执行。

**理由**
生产环境的隐式 DDL 是灾难：应用账号不应有 DDL 权限、变更无法审计、灰度/回滚无法控制、多实例同时启动可能并发建表。

**代价**
接入多一步（约 1 行）。

**被否决的替代方案**
- ❌ 首次连接自动建表 → 生产事故
- ❌ 内置完整迁移框架 → 重复造轮子且与用户的迁移工具冲突

## ADR-014 MIT 许可与"不商用"的澄清

**背景**
需求表述为"开源项目、不商用、MIT 协议"。但 **MIT 协议明确授予任何人商业使用权**——"不商用"与 MIT 之间存在字面矛盾，若不澄清会造成两种误读。

**决策**
采用 **MIT**，并在 README 与 PRD 中显式澄清：

> 本项目的"非商业"指**项目发起方不以盈利为目的**（不做商业版、不卖授权、不做 open core 裁剪），**不是限制使用者商用**。

**理由**
- 选 MIT 是为了最大化采用率与信任（无 copyleft 传染、企业法务无障碍）
- 若真的想"禁止他人商用"，必须改用 PolyForm Noncommercial / BSL 等**非 OSI 许可**，那就**不再是开源项目**

**代价**
无法通过许可获得任何商业回报（这是刻意的，也是定位的一部分）。

**被否决的替代方案**
- ❌ GPL/LGPL → 对企业采用有阻碍，与"最大化复用"目标相悖
- ❌ PolyForm Noncommercial → 不是开源许可，与"开源项目"定位冲突
- ❌ 参考 Golershop 的 open core（README 声明"非商业授权"但 LICENSE 文件是 LGPL-3.0，**自相矛盾**）→ 这种许可混乱会直接劝退使用者，我们刻意避免

## ADR-015 `SelfCheck()` 自检

**背景**
接入一个账务库时，最常见的失败不是"报错"，而是**静默的错误**：表没建全、`Maintain` 没挂、配置不自洽、余额与流水已经不一致。

**决策**
提供 `SelfCheck(ctx, tenantID) (Report, error)`，一次调用返回结构化报告：

- **Schema 检查**：7 张表是否全部存在，字段是否匹配
- **不变量检查**：`I1` 余额 == 流水和；`I2` 分佣总额 ≤ 可分配上限；`I3` 净佣金 ≥ 0
- **配置检查**：费率是否配置、层级是否超限、冻结期是否合理
- **计数统计**：各状态的佣金单/提现单数量（便于发现"卡住"的数据）

**理由**
**它是接入排障的唯一入口。** 有它，使用者能在 1 分钟内自诊 90% 的接入问题，而不必来提 issue。

**代价**
需要额外实现检查逻辑，且检查逻辑本身要保持与表结构同步。

**被否决的替代方案**
- ❌ 只提供日志 → 静默错误不会被发现
- ❌ 只提供 `HealthCheck` 返回 bool → 无法定位问题

而不是纸面推演——因此每个都配了对应的回归测试。

## ADR-016 端口定义在根包

**背景**
设计阶段把持久化端口规划在 `store/store.go`。写代码时发现这会形成导入环：
根包 `distledger` 需要引用 `Store` 类型来接受注入，而 `store/memory` 需要
引用根包的类型来实现它。若端口在 `store` 包，则 `distledger → store → distledger` 成环。

**决策**
`Store` / `Reader` / `Writer` / `Tx` 全部定义在**根包**（`store.go`），
实现放在 `store/memory`、`store/mysql`。依赖方向恒为「实现 → 根包」。

**理由**
这也是 Go 的既有惯例：**接口由消费方定义**，而不是由实现方定义。
消费方是根包的编排逻辑，因此接口理应待在根包。

**代价**
根包的文件数量增加；用户实现自定义 Store 时必须 `import distledger`。

**被否决的替代方案**
- ❌ 端口放 `store` 包 → 导入环
- ❌ 把领域类型下沉到 `internal/` → 外部用户无法引用 `Balance`、`Commission` 等返回类型
- ❌ 把公开类型另建一个 `core` 子包 → 用户要 import 两个包，违背"便捷接入"

## ADR-017 财务字段不可变，生命周期字段带版本 CAS

**背景**
ADR-004 说「佣金记录不可变」。但佣金单上有 `State`、`AvailableAt`、`SettledAt`
这些**必然**要随时间变化的字段。如果不把「不可变」精确到字段级别，
这条规则要么无法执行，要么会在实现时被打折扣。

**决策**
把佣金单的字段分成两类，并让 Store 端口强制这条分类：

| 类别 | 字段 | 可变性 |
|---|---|---|
| **财务字段** | `Key` `IdemKey` `OrderItemID` `BuyerUserID` `AgentUserID` `Layer` `BaseAmount` `Rate` `Amount` `FreezeDays` `RuleVersion` `RuleSnapshot` `AccruedAt` | 创建后**永不改变** |
| **生命周期字段** | `State` `AvailableAt` `SettledAt` `Version` | 可变，但每次变化必须携带 `Version` 做 CAS |

端口层只暴露 `AppendCommission` / `SetCommissionAvailableAt` / `TransitionCommission`，
**不存在通用的 `Update`**。

**理由**
"不可变"如果只写在文档里，就一定会在某次赶工中被绕过。让写接口的形状本身
只支持合法操作，代码评审就不再是最后一道防线。

**代价**
将来若要修正一笔佣金（例如发现计佣基数算错），不能原地改，只能冲正 + 重发。
这是可接受的：原地改会让审计链断裂。

**被否决的替代方案**
- ❌ 提供 `UpdateCommission` 让调用方自行保证只改生命周期字段 → 等于没有保证
- ❌ 用不可变事件溯源存全部变更 → v0.1 复杂度过高，且对内存 Store 不友好

## ADR-018 `PaidAt` 必填，且归因不追溯

**背景**
最初的设计里 `PaidAt` 是可选的，留空时取 `Clock` 当前时间。测试写完后发现：
如果首次投递时买家还没有绑定（因此没有产生佣金），之后有人补建了绑定再重放
同一事件，那么「当前时间」会晚于补建绑定的时间，于是这笔订单被**追认**归因。

这条路径就是「事后抢单」：任何人只要在看到订单之后把自己绑成买家的推广人，
再触发一次重放，就能拿走佣金。

**决策**
两道闸门同时上：

1. `PaidAt` 改为**必填**，库拒绝用当前时间代替。
2. 归因额外要求 `binding.BoundAt <= paidAt`，即绑定必须在支付时刻**已经存在**。

**理由**
追认归因是资损，而且是"看起来完全合法"的资损——账是平的、状态机是合法的、
幂等键是唯一的，只有业务语义错了。这类问题靠对账发现不了，只能靠拒绝实现。

**代价**
调用方必须提供支付时间（它本来就有）；重放事件时必须带上**原始的**支付时间。
后一点需要在接入文档里明确说明——见 README 的「三个必须知道的行为约定」。

**被否决的替代方案**
- ❌ 只做第 2 条 → 重放时若不带 `PaidAt` 仍会用当前时间，闸门失效
- ❌ 落一张「订单首次见到时间」的表 → v0.1 不引入额外实体；且那是 v0.3 的规则版本表该干的事

## ADR-019 中间层级不合格不截断关系链

**背景**
某一级分销员被禁用时，他**上面**的层级还要不要发佣金？两种做法都说得通。

**决策**
分两种情况处理：

- **第 1 级不合格**（订单归属的那个分销员）→ 归因本身无效，**整单不分佣**。
- **中间层级不合格** → 只跳过该级，**链条继续向上**。

**理由**
关系链是客观存在的拓扑，资格是个体的属性。如果让不合格节点截断链条，
一个被临时禁用的人会无声地吞掉他所有上级的收益——这类工单在客服侧
极难解释，也极难举证（上级看到的是「这单没产生收益」，而不是「某人被禁用了」）。

两种处理都写进 `AccrueResult.Skipped`，运维可以精确回答「谁、在哪一级、为什么没拿到」。

**代价**
与「链断在禁用节点」的实现相比，平台的佣金支出略高。

**被否决的替代方案**
- ❌ 一律截断 → 上级收益被下级的禁用状态"连坐"
- ❌ 一律跳过继续 → 第 1 级不合格时会把佣金发给一个与买家毫无关系的上级链，等于凭空发钱

## ADR-020 内存 Store 到期索引用混合快照回滚

**背景**
`pendingDue` 是按 `(到期时间, ID)` 有序的索引，支持二分定位到期项——
这让 `Maintain`（每分钟调用一次、永远调用）在没有到期项时是 O(1)。

但有序索引需要**中间插入**（新佣金到期时间早于已有条目）和**中间删除**。
这两种操作会搬移元素，于是「按长度截断」这种最廉价的回滚方式
会恢复出**元素错位**的内容。

这个缺陷在实现时被内部测试抓到了两次：
第一次是「先中间插入、再回滚」，第二次是「先尾部追加、再中间插入、再回滚」。

**决策**
对 `pendingDue` 采用**混合快照**：

- 尾部追加 → 只记录原始长度（O(1)）。
- 中间插入/删除 → 升级为全量克隆。**升级时克隆的是 `current[:原长度]`**，
  而不是整个 `current`——因为在此之前的变更都是尾部追加，
  前缀恰好就是事务开始时的内容。

**理由**
绝大多数追加发生在尾部（收货时间天然递增），因此快照几乎总是廉价的；
只有乱序收货才会触发克隆。用罕见路径上的一次拷贝，换掉一类
「回滚后数据看起来正常、实际错位」的隐蔽缺陷。

为什么必须专门测索引本身：读取路径带新鲜度校验，会静默跳过失效索引项。
这保护了正确性，但也意味着**索引错位不会表现为错误结果，只会表现为越来越慢**——
如果不直接比对索引快照，这类缺陷会以性能事故的形式在几个月后出现，届时无法归因。

**代价**
内部状态机比"全部全量快照"复杂；需要一组专门针对索引的内部测试来守住它。

**被否决的替代方案**
- ❌ 每次事务都全量快照索引 → 代价与数据总量成正比
- ❌ 用 map 代替有序切片 → 失去 O(log n) 的到期查询，`Maintain` 退化为 O(n)
- ❌ 事务内不物理删除、只做惰性失效 → 索引无限增长

## ADR-021 分页用键集而不是偏移

**背景**
`Reader` 提供若干列表查询（佣金、流水、账户）。两种分页方式：

- `OFFSET/LIMIT`：实现简单，但翻页时若有新记录追加，后续窗口整体后移，
  于是**有记录从未被读到**。
- 键集（`AfterID`）：以最后一条的 ID 为锚点，不随追加漂移。

**决策**
一律使用键集分页。账户没有自增 ID，因此用 `AfterUserID` 作为锚点
（并为此单独定义了 `AccountPage`，而不是硬塞进 `Page` 造成语义混淆）。

**理由**
这不是性能偏好，而是**正确性要求**。这些列表的主要消费者是 `SelfCheck`
对账：对账时一边翻页一边有流水追加是常态。漏读会让「账是平的」这个结论
不成立——而一个会给出错误肯定结论的对账工具，比没有对账工具更危险。

**代价**
调用方需要自己记住游标，不能随机跳页。对账与管理后台场景可以接受。

**被否决的替代方案**
- ❌ `OFFSET/LIMIT` → 对账漏读
- ❌ `AccountPage` 复用 `Page`（用 UserID 填 `AfterID`）→ 字段名与实际语义不符，是最容易写错的那种 API

## ADR-022 v0.1 不引入任何尚未落地的配置项

**背景**
设计阶段在 `Rules` 里规划了 `MinWithdraw`、`FeeRateBP` 等提现相关配置，
以及 `Commission.ReverseOf` 字段。这些要到 v0.5 / v0.3 才有实现。

**决策**
v0.1 **不引入**这些配置项与字段。同时清理了实现期产生的死代码
（`settleIdemKey`、未被使用的 `AgentKey` 与 `TenantScope` 类型）。

**理由**
这正是本项目批评 Golershop 的那件事：保留声明而摘掉实现，使用者无法判断
哪些能力真实存在，调用时才炸。既然我们把它写进了反面清单，就不该在自己
的代码里复制这个模式。

**空壳配置比缺功能更危险**：用户在 `Rules` 里设了 `MinWithdraw`、
程序不报错、行为上完全被忽略——他会以为起提门槛生效了。

**代价**
v0.3/v0.5 需要改动 `Rules` 与 `Commission` 的结构。在 v1.0 之前这是允许的。

**被否决的替代方案**
- ❌ 先留着字段占位 → 使用者会以为它生效
- ❌ 留着但注释「暂未实现」→ 注释不会在用户 IDE 的自动补全里出现

## ADR-023 处理时间来自 Clock，事件时间来自调用方

**背景**
v0.1 的 `Maintain(ctx, now)` 接受一个显式的 `now`，而 `clock.go` 又声明「库内部禁止直接调用
`time.Now()`，所有时间必须来自注入的 Clock」。两者互相矛盾，而且危险：时钟停在 1 月 1 日、
冻结期 3650 天，只要传入 `now + 4000 天` 就能立刻把全部待结算佣金转成可提现，没有任何告警。

**决策**
把时间分成两类，规则不同：

| 类别 | 例子 | 来源 |
|---|---|---|
| **事件时间** | `PaidAt`、`ReceivedAt`、`RefundedAt` | **调用方提供**，且必填 |
| **处理时间** | 「现在该结算了吗」 | **只能是注入的 Clock** |

因此 `Maintain` 的签名变成 `Maintain(ctx)`，去掉 `now` 参数。

**理由**
事件时间是业务事实，只有订单系统知道；库用它来判断归因时刻、冻结起点，它描述的是「过去发生过什么」。
处理时间描述的是「账务库自己认为现在几点」，它决定钱能不能动。让调用方推进处理时间，等于让调用方
决定什么时候发钱——那不是参数，那是权限。

**代价**
不能在一个进程里用同一个 Ledger 模拟多个时间点。要加速就需要注入 `ManualClock`（测试里正是这么做的）。

**被否决的替代方案**
- ❌ 保留 `now` 但校验它不超前于 Clock → 又回到「用调用方的时间」这个根本问题上
- ❌ 两个都从 Clock 取 → 事件时间必须来自业务系统，否则回填/补录数据无法处理

## ADR-024 退款必须携带幂等标识，并落一张退款凭证

**背景**
退款冲正最初设计成「按本次退款金额按比例冲正」。写完测试立刻发现两个方向都错：

- 重复投递同一次退款 → 冲正被执行两次（钱被扣两遍）。
- 想靠「累计退款额」去重 → 但累计额在第一次应用后就变了，第二次同额退款算出的累计值不同，
  于是**两次金额相同的真实退款**会被误判成新的一笔。

**根本问题**：在没有「这次退款是谁」的标识时，「同一次退款被重投」与「两次金额相同的真实退款」
在数据上**完全等价**。任何实现都只能二选一地做错。

**决策**
1. `OrderRefundedEvent.IdemKey` **必填**，语义是「这次退款在调用方系统中的标识」（通常是支付渠道的
   退款单号或调用方自己的退款流水号）。
2. 新增 `Refund` 凭证实体，每个「退款批次 × 计佣明细」一行，记录本次金额与**该明细的累计退款额**。
3. 幂等键按 `(租户, 订单, 明细, 调用方退款标识)` 派生；凭证插入冲突即代表这次退款已经应用过。

**理由**
这与 `PaidAt` 必填属于同一类判断：**当一个业务事实只有接入方知道时，就要求他提供，而不是自己猜。**
库不能凭空发明退款的同一性。

**代价**
接入方必须为每次退款生成或透传一个标识。这对任何真实系统都不是额外负担——退款本来就有单号。

**被否决的替代方案**
- ❌ 用「订单 + 退款金额」做键 → 两次金额相同的真实退款会被吞掉
- ❌ 用「订单 + 退款金额 + 调用时刻」做键 → 重投时时刻不同，等于没有去重
- ❌ 要求调用方自己保证不重投 → 这正是「把防重推给用户」的反模式

## ADR-025 冲正按「累计目标」而不是「本次增量」

**背景**
「本次该扣多少」这种增量式表达，在重试、乱序、分批这三件事上都会出问题。

**决策**
对每一笔受影响的佣金，先算出**按当前累计退款额它应当被冲正到多少**（`target`），
再与它当前的累计冲正额相减，只应用差额。差额 ≤ 0 就什么都不做。

```
target = 佣金金额 × 该明细累计退款额 ÷ 该明细计佣基数   （截断，且不超过佣金金额）
delta  = target − 已冲正累计额
```

**理由**
一个选择同时买到四个性质：

- **重复投递是空操作**：重算得到同一个 target，差额为 0。
- **分批自然累加**：第二批的 target 覆盖第一批的结果。
- **退款顺序无关**：target 只取决于累计额，与到达顺序无关。
- **不可能超额冲正**：target 被硬性封顶在原始金额。

**代价**
需要知道「该明细的累计退款额」，这正是 ADR-024 那张凭证存在的第二个理由。
另外截断会带来每笔最多 1 分的少冲正——刻意选择：多冲正要面对分销员的投诉，少冲一分不会。

**被否决的替代方案**
- ❌ 增量式（扣 `本次退款额 × 费率`）→ 重投即重复扣款
- ❌ 四舍五入 → 逐级累加后可能超过原始金额，破坏不变量 I3

## ADR-026 隔离而不是中止

**背景**
v0.1 的 `Maintain` 在遇到一笔「待结算但金额非正」的损坏记录时返回错误并中止。
后果是：一条坏记录让**该租户的全部分销员**都无法提现；而且由于错误直接返回，
循环里排在它后面的租户也一起停摆。

**决策**
1. 坏记录**隔离**：跳过它，把 ID 放进 `MaintainResult.Quarantined`，写一条 Warn 日志，
   健康记录照常结算。
2. 租户之间**互相隔离**：单个租户的错误被收集起来，其它租户继续，最后用 `errors.Join` 一并返回。

**理由**
资金系统的可用性问题会直接变成业务停摆。一条坏记录的成因需要人工介入，但那不该成为
所有人的钱都卡住的理由。**「失败要响亮」与「失败要局部」并不矛盾**：隔离不是静默——
它同时出现在返回值、日志和 `SelfCheck` 的不变量违规里。

**代价**
需要人工巡检 `Quarantined`。若没人看，坏记录会一直躺在那里——但它不会消失，
自检会持续报它。

**被否决的替代方案**
- ❌ 中止整批（v0.1 行为）→ 爆炸半径等于「全部租户」
- ❌ 静默跳过不报告 → 钱被藏起来，违反「不静默丢钱」原则
- ❌ 把坏记录改写成合法数据 → 库不该猜测损坏数据原本应该是什么

## ADR-027 自购默认不发佣

**背景**
分销员用自己的推广链接给自己下单，就能把自己的钱付给自己。这是分销体系里最常见的滥用形式，
而它有一个可怕的特点：**账目完全平衡**。流水守恒、状态机合法、配额正确，I1 与 I2 全部通过。
审计和推广链接本身都发现不了。

**决策**
默认资格判定器在两处拒绝：分销员必须处于启用状态，且**买家不能是分销员本人**。
`BindBuyer` 另有一道更早的闸门，拒绝把自己绑成自己的推广人。

**理由**
这是「默认不发钱」原则在资格维度的延伸。要开启自购返利（有些业务确实需要），
实现自己的 `EligibilityChecker` 即可——这正是规则层存在的意义。

**代价**
确实需要自购返利的业务要多写几行。除此之外没有代价。

**被否决的替代方案**
- ❌ 加一个 `SelfPurchase bool` 配置 → 又一个「默认值决定事故形态」的开关（见 ADR-010）
- ❌ 完全不管 → 这是能被系统性利用的资损面，而且查不出来

## ADR-028 工作量的上界属于架构，不属于业务

**背景**
`OrderPaidEvent.Items` 原本没有数量上界，且允许 0 元明细。两者叠加的问题不是「业务上不该这样」，
而是**工作量不可预测**：分佣发生在持有全局写锁的事务里，一个携带十万条明细的请求就能让所有租户的
账务停住几十毫秒；而 0 元明细还能绕过「明细之和 ≤ 实付金额」的校验，用极低的代价制造这种停顿。

**决策**
1. `MaxOrderItems = 200`，超出直接拒绝。
2. 明细金额必须 **> 0**。
3. 退款事件同样受明细数量上界约束；`Maintain` 单次调用有批次上界。

**理由**
「有没有上界」看起来像业务参数，实际是架构属性：它决定尾延迟是否可预测，而资金系统的尾延迟
会直接表现为别人的账被卡住。0 元明细被拒绝还额外买到一件事——把一个静默的空操作变成响亮的报错，
而 0 元明细几乎总是字段映射错误，不是礼物。

**代价**
确实超过 200 个明细的订单需要拆成多次调用或走自定义实现。这在电商场景里极少见。

**被否决的替代方案**
- ❌ 设成可配置 → 给了一个「把系统打挂」的旋钮
- ❌ 允许 0 元明细并只限制数量 → 上界内的工作量仍然被无意义地放大

---

# 审查驱动的结构性修复

以下四条来自 v0.1 的对抗性代码审查。它们的共同特征：**不是修一个 bug，而是修掉让那类 bug
得以存在并再次发生的东西**。

---

## ADR-029 资金桶只能有一处定义

**背景**
`Account` 有若干资金字段，但每一个检查都各自手写了字段名：

- `Settleable()`：`a.Frozen >= 0 && a.Available >= 0 && ...`
- 不变量 I1：声明四个 `sum*` 变量、四个 `Add` 调用、四个相等比较、四个尾部比较

后果在 v0.1 真实发生了：`TotalEarned`（面向分销员展示的**累计收益**）落在所有这些检查之外。
把它改成 `-999999.99` 之后，账是平的、自检 `OK=true`、只有用户看到的数字是错的——
正是这个库声称要消灭的那类静默错误。v0.3 新增 `TotalReversed` 时，同样的陷阱会原样重演。

**决策**
引入 `Bucket` 类型，把资金桶的定义收敛到**唯一一处**：

```go
func AllBuckets() []Bucket          // 桶集合
func (b Bucket) Value(a Account) Money
func (b Bucket) Set(a *Account, v Money)
func (b Bucket) Delta(e LedgerEntry) Money
func (b Bucket) After(e LedgerEntry) Money
```

- `Settleable()` 遍历 `AllBuckets()`
- I1 遍历 `AllBuckets()` 求和与比对
- 流水构造（`newLedgerEntry`）遍历 `AllBuckets()` 写 `After*`，并只写被移动那个桶的增量
- 冲正的资金桶选择从私有的 `reversalBucketKind` 枚举改为直接返回 `Bucket`——**并行枚举本身就是第二个会被遗忘的地方**

**怎么保证它不再腐化**
`model_test.go` 用反射枚举 `Account` 的全部 `Money` 字段，要求每一个要么是桶、要么在
`exemptTotals` 里显式登记并写明由哪条不变量覆盖。新增字段会让测试**失败**，直到有人做出选择。

这是这条 ADR 的核心：**把「记得加检查」从人的自觉变成编译期/测试期可见的约束。**

**代价**
多了一层间接（`b.Value(a)` 而不是 `a.Frozen`），热点路径上有一次 switch。相对「不变量随时间腐化」，这个代价可以忽略。

**被否决的替代方案**
- ❌ 只把 `TotalEarned` 补进 I1 → 修了一个字段，没修产生它的机制
- ❌ 用反射在运行时遍历 Account → 生产代码依赖反射，与「零魔法」相悖；测试期用反射才是合适的边界
- ❌ 把桶改成 `map[string]Money` → 失去编译期字段检查，且热路径上引入 map 开销

## ADR-030 重试的定义必须先回滚再重跑

**背景**
`Store` 的文档说「实现可以因为版本冲突而重试整个函数」，但**没有说清重试之前是否回滚**。
审查指出：若某个实现「不回滚直接重跑」，`settleOne`（先迁移状态、后动钱）会在第二次执行时
看到自己上一次留下的 `Settled` 状态，于是把它当成「已被并发处理」而跳过——结果是
**佣金被标成已结算，但钱从未从待结算移到可提现**，且 `Maintain` 认为这笔已由他人处理，不再重试。

v0.1 的内存 store 永不冲突（全局写锁），所以这条契约从未被执行过，缺陷也就从未暴露。

**决策**
把重试的定义写死，不留解释空间：

> "Retry" means exactly this, and nothing weaker:
> 1. the failed attempt is rolled back completely, and
> 2. the function is invoked again against the state as it was BEFORE that attempt.
>
> Retrying without rolling back first is not permitted.

同时补一个测试：一个包装 store，把更新函数「执行一次 → 强制失败回滚 → 再执行一次」，
验证引擎在重试下不重复计数（`Commissions` 不翻倍、账户余额正确、自检通过）。

**理由**
引擎的正确性依赖「每次进入回调时世界都是干净的」这一前提，而它此前只是隐含在实现里。
把前提写成契约，并**为它写一个会失败的测试**，是从「依赖实现巧合」变成「依赖接口契约」。

**代价**
任何想在冲突时不回滚就重试的实现都被明确禁止。这限制了一种（本来就错误的）优化空间。

**被否决的替代方案**
- ❌ 让 `TransitionCommission` 在「状态已是目标态」时返回成功 → 会把「我做的」和「别人做的」混为一谈，
  而结算必须先确认是自己完成的状态迁移，才能据此动钱
- ❌ 只在文档里加一句「建议回滚」→ 建议不是契约

## ADR-031 未分摊的计佣基数必须可见

**背景**
`Items` 定义每个明细的计佣基数，`PaidAmount` 是实付金额。校验只拦「明细之和 > 实付金额」。
于是「明细之和 < 实付金额」被静默接受：调用方漏报一个明细，佣金按较小的基数计算，
返回的是 `err=nil`、`Attributed=true`、一个正常的正整数佣金——**与一次完全成功的入账长得一模一样**。

**决策**
`AccrueResult.UnallocatedBase` 报告「实付金额里没有被任何明细认领的部分」。

**理由**
明细之和小于实付金额是**合法的**（运费、赠品、不计佣商品），所以简单要求两者相等会误伤真实业务。
但「合法」不等于「应该无声」。把差额变成一个返回值里的数字，调用方就能自己判断这是设计如此还是漏报——
**把一个静默的少算变成一个可观察的事实**，这正是 R6「可追溯」的目的。

**代价**
多一个返回字段。调用方若忽略它，行为与从前一样（仍然少算），所以这条修复的价值取决于文档是否说清。

**被否决的替代方案**
- ❌ 要求 `sum(Items) == PaidAmount` → 把合法的「部分明细参与计佣」判成非法
- ❌ 在 `Skipped` 里记一条 → `Skipped` 的语义是「某一级为什么没发钱」，不是「基数去哪了」

## ADR-032 佣金金额的符号必须与冲正链接一致

**背景**
`AppendCommission` 是存储层唯一的佣金写入口。v0.1 不校验任何金额符号或链接，因此可以写入
`Amount <= 0` 且没有 `ReverseOf` 的记录——引擎既无法解释它（不是入账也不是冲正），
也无法对账（I3 的「累计额 ↔ 明细」对不上）。审查已证明，一条这样的记录能让 `Maintain`
对**整个租户**永久失败。v0.3 引入负数冲正记录之后，这个口子是双向的。

**决策**
`AppendCommission` 强制三条：

| 条件 | 结论 |
|---|---|
| `Amount == 0` | 拒绝：零额佣金没有意义，应当直接不创建 |
| `Amount < 0` | 必须 `ReverseOf > 0`（它是对某笔入账的冲正） |
| `Amount > 0` | 必须 `ReverseOf == 0`（入账不指向别的佣金） |

**理由**
端口形状是我们用来保证不变量、而不是靠代码评审的地方（ADR-017 已确立这个原则）。
金额符号与链接的一致性属于同一类：**让不合法的记录在写入时就不可能存在**，
比让它存在之后再靠 `Maintain` 的防御性检查去发现要好得多。

顺带把「坏记录」的测试替身从「零额佣金」（现在写不进去了）换成更真实的形态：
一笔「累计冲正额等于金额、却仍处于待结算」的佣金——引擎永远不会产生这种组合。

**代价**
测试或运维需要用直接写库的方式构造损坏数据时必须绕过校验。这是可接受的：绕过校验本来就该是显式行为。

**被否决的替代方案**
- ❌ 只在 `Maintain` 里防御 → 坏数据已经落库，而落库的坏数据会一直存在
- ❌ 在 store 里根据 `Amount` 自动推断 `ReverseOf` → 库不该猜测意图

---

# 多后端带来的决策

模块化存储（MySQL / PostgreSQL / SQLite 由使用者自选）不是一个打包问题，而是一个**接口设计问题**。
以下两条是这次需求逼出来的，其中第二条修正了一条被内存实现掩盖了很久的契约缺陷。

---

## ADR-033 一个 SQL 内核加多个薄方言

**背景**
「存储要模块化，MySQL、PostgreSQL 等自己选」有两条实现路线：

- **A：每个数据库一份完整实现。** `store/mysql`、`store/postgres`、`store/sqlite` 各自实现全部 26 个端口方法。
- **B：一个可移植内核 + 多个薄方言。** 语句拼装、行扫描、事务与重试、乐观锁、幂等冲突处理全部只写一遍；
  每个驱动包只提供方言差异。

**决策**
选 B。结构如下：

```
store/
├── memory/      # 内存实现，零外部依赖
└── sql/         # 可移植内核：实现 distledger.Store，通过 Dialect 拼装语句
store/mysql/     # 只提供 Dialect + Open(*sql.DB)
store/postgres/
store/sqlite/
```

`Dialect` 的职责被刻意压到最小——只包含**真正因数据库而异**的东西：

| 职责 | 差异来源 |
|---|---|
| 占位符 | `?`（MySQL/SQLite）对 `$1`（PostgreSQL） |
| upsert 子句 | `ON DUPLICATE KEY UPDATE` / `ON CONFLICT ... DO UPDATE` |
| 重复键判定 | 错误码 1062 / SQLSTATE 23505 / 约束名 |
| 可重试错误判定 | 死锁、序列化失败的错误码各不相同 |
| 标识符引用 | 反引号对双引号 |
| 建表 DDL | 类型名与索引语法不同 |

**理由**
端口已经有 26 个方法，而且每一个都涉及事务、乐观锁与幂等冲突。把这份逻辑复制三遍，
意味着**任何一次不变量相关的修复都要改三处，而漏掉一处不会报错**——这正是本项目一直在消灭的缺陷形态。
选 A 的代价不是写三倍的代码，是**三份会各自漂移的账务逻辑**。

反过来看，方言差异的总量很小且都是机械的：一个方言大约 100–150 行，其中大部分是常量表。
新增一个后端（SQL Server、Oracle、TiDB）等于写一个方言，而不是再写一个 store。

**代价**
可移植内核必须只用各数据库的**交集**能力，因此放弃了一些方言特有的优化（例如 PostgreSQL 的
`RETURNING`、MySQL 的 `INSERT ... ON DUPLICATE KEY UPDATE ... RETURNING`）。可移植优先于单库最优。

**被否决的替代方案**
- ❌ A：每库一份实现 —— 三份会漂移的账务逻辑
- ❌ 用 ORM（GORM / ent）统一 —— 违反零依赖原则，且 ORM 会隐藏我们刻意要显式控制的锁与隔离语义
- ❌ 只支持一个数据库 —— 使用者的技术栈不由我们决定

## ADR-034 按「需求最小的后端」写端口，而不是按现有实现

**背景**
`Reader.Tenants()` 在内存实现里是遍历四张 map 取并集——O(全部数据)，但内存里很快，所以一直没人注意。
v0.1 的审查已经指出 `Maintain` 每次心跳都调它会做一次全量扫描（P2-3），当时被归为性能优化。

**这个需求改变了它的性质**：在 SQL 后端里，「四张表取并集再去重」不再是「有点慢」，而是
`SELECT DISTINCT tenant_id FROM dist_agent UNION SELECT ... FROM dist_account UNION ...`——
跨几张最大的表做去重，且**每分钟执行一次**。

**决策**
`Reader.Tenants()` 的契约明确要求：**实现必须维护一张租户登记表，不得通过扫描数据集回答**。
内存实现改为维护一个有序的已见租户切片（首次写入时登记），SQL 后端对应一张 `dist_tenant` 小表。

**理由**
这是一个更一般的教训：**内存实现会让某些契约缺陷隐身。**

内存里，「遍历四张 map」和「查一张登记表」的差别是微秒级，所以审查时容易放过；
而同一个接口在 SQL 上的差别是「扫描全表」对「一次索引查找」。**端口的契约应该按最苛刻的后端来写**，
否则它只是在描述当前那个实现，而不是在描述一个接口。

顺带这件事也修正了 v0.1 审查里的 P2-3：`Maintain` 的空转成本不再随数据总量增长。

**代价**
每个实现都要维护登记表，并且要在**所有**写路径上登记（内存实现里有 6 处调用点）。
测试上补了「每种首次写入都能登记租户」与「回滚必须撤销登记」两条，防止漏掉某个路径。

**被否决的替代方案**
- ❌ 保留并集实现，只给 SQL 优化 → 端口契约继续描述内存实现，而不是接口
- ❌ 把租户列表改成 `Maintain` 的参数 → 把维护租户清单的责任推给使用者，而库本来就能自己知道
- ❌ 引入真正的租户实体表并要求使用者维护 → 租户属于使用者的领域模型（ADR-001），库只把它当分区键；登记表是**索引**不是实体

## ADR-035 端口按「工作」提问，而不是按「实体」

**状态**：取代 ADR-034 的解决方案部分（ADR-034 的问题陈述仍然成立，且被这条进一步坐实）。

**背景**
ADR-034 认定 `Reader.Tenants()` 不应扫描数据集，于是给内存实现加了租户登记表、
给 SQL 后端设计了 `dist_tenant` 小表。这确实把「取租户列表」从 O(全量数据) 降到了 O(租户数)。

**但那次修法没有触及成本结构。** 真正的问题在 `Maintain`：

```go
tenants := r.Tenants(ctx)          // O(租户数)，修好了
for _, t := range tenants {
    l.maintainTenant(ctx, t, now)  // ← O(租户数) 次事务，一次没少
}
```

5000 个租户就是每分钟 5000 次 `BeginTx`/`Commit`，**即使全库没有任何到期佣金**。
按每次 1–3 ms 估算，纯开销 5–15 秒/分钟，并产生 5000 个数据库事务 ID 与相应的 undo/redo 日志。
租户数再翻一倍就翻一倍。

**决策**
端口不再问「有哪些租户」，改问「有哪些活」：

```go
TenantsWithDueWork(ctx context.Context, dueAt time.Time, limit int) ([]int64, error)
```

`Tenants()` 与租户登记表一并删除。

**理由**
这背后是一条比性能更基本的判断：

> **库不拥有租户，所以它没有资格枚举租户。**
> 租户属于接入方的领域模型（ADR-001），库只把它当作数据分区键。
> 库拥有的是「工作」，因此它应该问的是工作。

「列出所有租户」这个接口从来没有真正的消费者——`Maintain` 是唯一调用方，而它想要的其实是工作。
**一个只有引擎内部调用、而且问错了问题的接口，说明抽象层次错了，而不是说明需要优化它。**

**代价**
1. 需要索引 `(state, available_at, tenant_id)` 而不是 `(tenant_id, state, available_at, id)`。
   **列序是承重的**：以 `tenant_id` 打头会让跨租户查询退化为扫描排在最前面那个租户的全部积压，
   一个租户的积压会拖慢所有其它租户。改列序在功能上不报错，只在压力下变慢，
   因此测试**直接断言列序**。
2. `dist_tenant` 表被移除，上一版加在六条写路径上的租户登记也被移除——
   那是一次**写放大**，加在了最热的路径上。
3. 内存实现的 `TenantsWithDueWork` 需要利用「`pendingDue` 按 (tenant, at, id) 有序、
   每个租户的条目连续」这一性质：检查每个租户块的头即可判断它有没有活，然后用二分跳到下一个租户块。

**成本用测试固定，而不是用结果固定**
「按租户循环」与「按工作循环」两种实现**结算结果完全相同**，所以任何断言结果的测试都看不出区别。
差别只在规模上暴露——那是最不该发现它的地方。
因此测试**数操作次数**：N 个空闲租户、无到期项时，必须**恰好 1 次读、0 次事务**。

**被否决的替代方案**
- ❌ 只把「取租户列表」变便宜（即 ADR-034 的做法）→ 成本结构没变，只换掉了循环前的那一次扫描
- ❌ 给 `Maintain` 传租户参数 → 把维护租户清单的责任推给使用者，而库本来就能自己知道哪里有活
- ❌ 保留 `Tenants()` 供运维使用 → 没有真实消费者；一个没人用的接口会腐化，而且它的存在会让人以为心跳该这么写

## ADR-036 方言的差异要按「事务语义」而不是「语法」来划分

**背景**
ADR-033 把可移植内核与方言分开，并假设方言差异是**机械的**：占位符、引号、类型名、
自增形式、索引 DDL。写 `store/sql` 主体时，第一轮集成测试就否掉了这个假设。

`AppendCommission` 与 `AppendRefund` 的幂等性依赖唯一约束。内核对重复键的处理是
「插入，捕获重复键错误，返回 `ErrDuplicate`」。这在 MySQL 与 SQLite 上成立——
两者的约束错误只中止**该语句**，事务仍然可用。

**在 PostgreSQL 上不成立**：任何语句失败都会**中止整个事务**，后续语句一律报
`current transaction is aborted`，最终 `COMMIT` 变成 `commit unexpectedly resulted in rollback`。
「插入并捕获错误」这个模式在 PG 上根本不可用。

这不是语法差异——`INSERT` 的写法在三个库里是一样的。**这是事务语义差异**，
而它决定了控制流的形状。

**决策**
`Dialect` 增加一个方法，专门表达这一条：

```go
// InsertConflictClause 返回把唯一约束冲突变成空操作插入的子句；
// 返回空串表示该方言以错误形式报告冲突。
//
//   PostgreSQL: " ON CONFLICT DO NOTHING"
//   MySQL / SQLite: ""
InsertConflictClause() string
```

内核对插入的处理分两条路径：

- **有子句**（PG）：语句自身吸收冲突，内核从**影响行数**（或 `RETURNING` 无行）判断结果
- **无子句**（MySQL / SQLite）：语句抛错，内核用错误分类判断

**理由**
关键判断是：**能不能「失败了再继续」**。PG 不能，所以冲突必须在语句内部被吸收；
MySQL 与 SQLite 能，所以错误分类就够了。

顺带拒绝了 MySQL 的 `INSERT IGNORE`：它不只是忽略重复键，而是**忽略所有错误**，
包括 `NOT NULL` 违反与截断。那会把一次真实的数据错误变成一行被静默跳过的数据——
正是本项目一直在消灭的东西。`ON CONFLICT DO NOTHING` 只吸收约束冲突，其他错误照常抛出。

**代价**
`Dialect` 的方法从「纯语法」扩展到「事务语义」，接口的语义边界因此变宽了一点。
这是必要的：如果坚持方言只描述语法，这条差异就会以「PG 上退款重投会失败」的形式
藏在业务逻辑里，而不是出现在方言契约上。

**被否决的替代方案**
- ❌ 用 SAVEPOINT 包住可能冲突的插入 → 可移植且精确，但给每次插入都加一对往返；
  只有 PG 需要，而 PG 有更好的原生子句
- ❌ MySQL 用 `INSERT IGNORE` → 吞掉所有错误，把数据错误变成静默跳过
- ❌ 让 PG 也走「捕获错误」→ 事务已被毒化，无法恢复
- ❌ 只在文档里记一句「PG 需要特殊处理」→ 注释不会在编译期或测试期提醒任何人

## ADR-037 资金流动用增量，而不是读-改-写加版本比较

**背景**
引擎移动资金的原始形态是**读-改-写**：读 `Account` → 改两个桶 → `PutAccount`（带 `version` CAS）。

这在功能上正确，在规模上不成立。分销业务的特征是**热点集中**：大量订单归属于同一个头部分销员
（头部 KOL、大团长、门店导购）。5000 TPS 里若有 20% 落在同一个账户上，就是 1000 TPS 争抢一行。
乐观锁下除一个之外全部版本不匹配，全部重试整个 `OnOrderPaid` 事件。

幂等保证了不会算错钱，但吞吐随热点集中度下降，而热点集中不是异常，是这类业务的常态。

**决策**
端口新增原子增量：

```go
type AccountDelta struct {
    Key UserKey
    Frozen, Available, Withdrawing, Withdrawn Money
    TotalEarned, TotalReversed Money
    At time.Time
    RequireNonNegative bool
}

IncrementAccount(ctx context.Context, delta AccountDelta) (Account, error)
```

引擎的三处资金变动——分佣入账、结算、冲正扣款——全部改用它。

**理由**
两个关键点：

**第一，守卫必须在同一条语句内。** `RequireNonNegative` 不是「读出来比较，再写回去」，
而是 `UPDATE ... WHERE frozen + ? >= 0 AND ...` 的谓词。先检查再写入是两个语句，
中间可以插入别的写者。在结算（`frozen` 必须覆盖要转出的金额）与冲正（桶不能变负）上，
那个窗口就是丢钱。

**第二，增量比重试 CAS 高一个量级。** 重试让每个写者都要处理失败、退避、再试；
增量让数据库用自己的行锁串行化它们。在热门账户上，这不是微优化而是量级差别。

**一个副产品**：`PutAccount` 的语义因此收窄了。它现在表示「我认为当前值是这个，把它设成那个」，
即**管理性调整**（对账修复、数据迁移）。这恰好是「有人改了余额却忘了写流水」的形态——
也就是不变量 I1 存在的理由——因此自检测试正是用它注入损坏数据。

**代价**
1. 端口多了一个方法，两个实现都要写。内存实现里它是平凡的（写锁已保证原子性），
   SQL 实现要多一条带守卫的 `UPDATE` 加一次回读。
2. 增量语义无法表达「无论如何设为 X」——那仍然需要 `PutAccount`，所以两个方法都保留。
   它们不是重复：一个是「加」，一个是「设」。

**验证**
`TestEngineConcurrentOrdersToOneAgent` 让 12 个订单**全部归属同一个分销员**并发提交，
断言两件事：**失败数为 0**，以及最终余额**恰好**等于各笔之和。

第二条断言是刻意的：**丢失更新表现为「少钱」而不是报错**，
只断言「没有 error」的测试会完整地放过它。

**被否决的替代方案**
- ❌ 保留读-改-写，只在冲突时重试 → 热点上重试率极高，且每次重试都重放整个事件
- ❌ 用 `SELECT ... FOR UPDATE` 先锁行再读改写 → 也能解决，但那是在应用层重新实现
  数据库已经会做的事，且多一次往返
- ❌ 只把守卫留在 Go 里（读出来比较）→ 检查与写入之间的窗口就是丢钱
- ❌ 用 `PutAccount` 传绝对值来「模拟」增量 → 那正是丢失更新的来源

## ADR-038：「0 行受影响」不是单一语义

**背景**
`IncrementAccount`（ADR-037）用「先 UPDATE、受影响 0 行则查行在不在」来决定下一步。
这条推断在并发下是错的，曾把一个 **+5.00 的计佣**报成 `ErrInsufficientBalance`
（详见 `docs/fault-reviews/2026-02-11-首次计佣并发时误报余额不足.md`）。

**决策**
一条写语句返回「0 行受影响」时，必须**枚举它的全部来源**，而不是只处理最常见的那一种：

| 来源 | 正确响应 |
|---|---|
| 目标行不存在 | 创建它 |
| 行存在，但守卫条件不满足 | 拒绝，并说明是哪个桶 |
| **行在语句执行之后才出现** | **重试**——这条语句什么都没做 |

第三种最容易被漏掉，因为它在单线程下不可构造，而且和「守卫拒绝」在代码里长得一样。

**如何区分后两者**
不能靠「行存在吗」——两种情况下行都存在。要靠**这次操作在当前状态下是否解释得通**：
若把增量应用到刚读到的行上不会产生非法状态，那么「守卫拒绝」这个解释就站不住脚，
只剩下「语句错过了行」，于是重试。

**为什么增量写入尤其需要这条规则**
版本 CAS 的写入自带判断依据：版本不匹配就是明确的冲突。增量写入**没有这个信号**
——这正是 ADR-037 用热点性能换来的成本，本 ADR 是该成本必须配的补偿。

**代价**
分支变复杂了，且必须为「重试后依然失败」设一个上限，否则会变成活锁。
本库取两次：一次常规 + 一次给竞争窗口，第二次仍失败才报 `ConflictError`。

**被否决的替代方案**
- ❌ 一律报 `ConflictError` 让调用方重试 → 把库能自行消解的竞态外推给每个调用方；
  实测首次计佣并发时 12 笔会失败 5 笔
- ❌ 改用 `INSERT ... ON CONFLICT DO UPDATE` 一步到位 → 覆盖语义而非累加，
  且 MySQL / PostgreSQL / SQLite 三种写法各不相同，会把方言差异从 DDL 扩散到热路径
- ❌ 给账户表加「已存在」缓存 → 缓存本身也要处理失效，把竞态换了个地方而已

**验证**
`TestEngineConcurrentOrdersToOneAgent` 连续 25 次通过（修复前 10 次失败 6 次）。

## ADR-039：索引名由列推导，不由位置决定

**背景**
索引名曾是 `table_kind_序号`。索引名一旦编码「它在列表里排第几」，列表一变它就换了含义：
老版本迁移出来的库里 `dist_commission_idx_3` 是旧的列组合，而按新列表新建的库里
同名索引是**另一组列**。同一版本、两个部署、一个标识符指向两种东西。

**决策**
索引名 = `表_类型_列1_列2_...`。

**理由**
1. **名字是定义的函数**，不会随列表顺序漂移，两个部署上的同名索引必然同义。
2. **EXPLAIN 输出里自解释**——而索引名实际上主要就是在 EXPLAIN 里被读的。
3. 长度超限时截断（后端限额取最短的那个：PostgreSQL 63 字节），
   截断保留**前导列**，而前导列正是决定索引能否被用上的部分。

**代价**
名字变长；且今后真要改名会比改一个序号麻烦得多——这是把「改名的难度」
换成了「同名的危险」，而后者是静默的。

**验证**
`schema_test.go` 断言两条性质：名字等于列推导结果；**重排列顺序不会改名**。
另有测试断言没有任何名字超过后端限额、且不存在两个索引重名。

## ADR-040：工作预算是共享额度，不是每层循环各一份

**背景**
`Maintain` 有内外两层循环，各自带轮数上限。`maxSettlePerMaintain` 原先**只在外层轮次开头检查**，
而内层单个租户还能再结算 `maxMaintainRounds × maintainBatch = 20000` 笔。
于是真正的上界是「**租户数 × 20000**」而不是 20000。

实测（30 租户 × 900 笔，共 27000 笔到期）：

```
one Maintain call settled 27000 commissions; the budget is 20000
```

**决策**
预算是**一个对象**，被所有会花掉它的循环共享；谁花的谁记账。

三条配套规则都是承重的：

1. **只在事务提交后记账。** store 会重跑整个闭包来做回滚重试，在闭包里扣账会把回滚掉的工作也算进去。
2. **读取也受预算约束**（`permits`），不只约束写入。否则预算只剩 3 笔时仍会去读满一批 200 笔。
3. **在每个租户之前检查**，而不是在一轮之后。少一次检查，就多一整轮的乘以租户数的超支。

**为什么这条重要**
`Maintain` 由每分钟一次的定时任务驱动。一个「能被积压撑到任意大」的 tick，
迟早会跑过它自己的间隔，届时不是变慢而是叠加。

**代价**
所有会结算的入口都要带一个 `*workBudget` 参数。这是刻意的：
预算是**一次调用的属性**，把它作为参数显式传递，比藏成字段或全局变量更能防止漏记。

**验证**
`TestMaintainWorkBudgetIsACeilingNotAPerLoopLimit` 断言预算被**用满**（`== 20000`）而不只是「没超过」——
否则一个被其它 bug 悄悄压成 0 的预算也能通过。去掉预算后该测试报 27000。

**被否决的替代方案**
- ❌ 只调小 `maxMaintainRounds` → 改的是一个循环的上限，而问题在于上限相乘
- ❌ 在外层每轮之后累加检查 → 已经超支的那一轮已经跑完了
- ❌ 用 `context.WithTimeout` 兜底 → 超时是不可预测的中断，不是可预测的工作量；二者都需要，不能互相替代
